Evals

Numbers that move when you change a prompt

Why a unit test cannot do this

A unit test asserts fixed input gives fixed output. A model rarely does that, even at temperature zero.
flowchart TD A["Unit evals
plan validity, schema conformance
deterministic · milliseconds"] --> B["Component evals
grader precision, recall@k
labelled set · seconds"] B --> C["End-to-end
golden runs, real fixtures
tolerances · minutes"] C --> D["LLM-as-judge
quality against a rubric
expensive · drifts"] A -.- G1["blocks merges"] B -.- G1 C -.- G2["pages on a trend"] D -.- G2

Evals assert properties of behaviour instead of exact output. Running only the expensive top layer is the common mistake, and it makes the suite too slow to block a merge.

Split by determinism, not by speed. Real solvers differ at the last decimal, so an intermittent red build teaches people to ignore red builds.

Metrics with targets

Five numbers that say whether the system is healthy.
Metric Definition Target
Plan validity rate Plans passing validation first try ≥ 90%
Unassisted completion Runs finishing with no approval or escalation ≥ 70%
Time-to-diagnose Failure to proposed fix < 60 s
Cost per run Total LLM spend Well under the cap
Grader precision correct verdicts confirmed on a frozen set ≥ 85%
A rising escalation rate is not automatically bad. If every escalation is a correct "I don't know", the system is fine and the corpora are the gap. Read escalation rate next to grader precision, never alone.

Where the eval set comes from

Nobody has one on day one. You harvest it, and the harvesting has to be designed in first.
flowchart LR P["Every grader call
in production"] --> L["Logs one row
(query, evidence, verdict, reason, model)"] L --> H["Hand-label a few hundred"] H --> F["Frozen eval set"] F --> CI["Runs in CI"] F --> HO["Hold out a slice
you never tune against"]

The usual failure is waiting until you need a set to start building one. Then the only option is synthetic cases that share none of production's weirdness.

Source Good for Watch out
Sampled production Realistic distribution Over-represents the easy case
Escalations and overrides Hard cases a person already flagged Biased to failure; keep successes too
Past incidents Regressions you already paid for Small; keep each forever
Synthetic and adversarial Rare and hostile inputs Never a substitute for real traffic

Freeze and version it. A set that drifts with the system measures nothing.

Roll out keyed on tenant so one customer sees one consistent system, rather than a coin flip per request.

Optimising into a worse system

Symptom: escalation rate drops, everyone celebrates, human-override rate climbs a month later.

Cause: the change made the system more willing to answer, not more likely to be right. Escalation rate alone rewards confidence.

Mitigation: never read it without grader precision beside it.

Judges drift

Use a judge only where no deterministic check exists, then pin it.
Grader drift

Symptom: escalation rate creeps up over weeks with no code change.

Cause: the model moved behind a floating alias, or a prompt edit shifted the boundary between ambiguous and incorrect.

Mitigation: pin exact model IDs. Run the frozen set in CI on every prompt or model change, and alert on a shift in the verdict distribution.

Make the grader testable in isolation: strict schema, temperature zero, a parsed object rather than free text. Then every production call logs a gradeable tuple.

The trace is the eval you did not write

One run is one trace, with workflow, activities and model calls in the same tree.
flowchart TD W["invoke_workflow"] --> E["execute_step activity"] W --> D["diagnose_failure activity"] E --> L1["chat sonnet-5"] E --> T1["tool: set_field"] T1 --> H["HTTP span"] D --> L2["chat haiku-4-5 (grader)"] D --> T2["tool: search_logs"]

Use the standard GenAI span attributes rather than inventing your own: gen_ai.provider.name, gen_ai.request.model, gen_ai.usage.input_tokens.

Keep prompt content out of the tracing backend. Store it externally and put a reference on the span. Telemetry has a different retention policy and a different access list.

Takeaways

  • Build the pyramid bottom-up. Deterministic checks catch most regressions for milliseconds.
  • Deterministic evals block merges; golden runs page on a trend.
  • Log gradeable tuples in production before you need an eval set.
  • Freeze and version the set, and hold out a slice you never tune against.
  • Pin judge model IDs, and alert on verdict-distribution shift.
  • Never read escalation rate without grader precision beside it.
