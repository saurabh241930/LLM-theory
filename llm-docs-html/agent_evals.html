Evaluating Agent Systems

The eval pyramid, metrics that move, and judges that drift

Why a unit test cannot do this job

A unit test asserts a fixed input produces a fixed output. An LLM rarely does that, even at temperature zero, and never across model versions.

Evals assert properties of behaviour instead of exact output, and they work at four levels with very different cost and very different failure coverage. Running only the expensive top layer is the common mistake, and it produces a suite too slow to block a merge.

Cheap and deterministic at the base; expensive and judgement-based at the top.

Split the suite by determinism, not by speed. Deterministic evals block merges. Golden runs page only on a trend, because a real solver is non-deterministic at the last decimal and an intermittent red build teaches people to ignore red builds.

Metrics with targets

Five numbers that tell you whether the system is healthy, each with a target somebody committed to.
Metric Definition Target
Plan validity rate Planner outputs passing DAG validation on the first attempt ≥ 90%
Unassisted completion rate Runs reaching completion with zero approvals or escalations ≥ 70%
Mean time-to-diagnose Wall clock from a failed state to a proposed remediation < 60 s budget, ~15 s typical
Cost per run Total LLM spend across one run Well under the $25 ceiling
Grader precision correct verdicts confirmed against the frozen labelled set ≥ 85%
A prompt change becomes a number that moves, rather than an opinion about whether it felt better.
A rising escalation rate is not automatically bad. If every escalation is a correct "I don't know", the system is behaving well and the corpora are the gap. Read escalation rate next to grader precision, never alone.

Golden runs against real fixtures

A fixed input/output pair used as a regression check, run against the real system rather than a mock.
@pytest.mark.parametrize("golden", GOLDEN_RUNS, ids=lambda g: g.id)
def test_golden_run(golden, session_glow, function_project, is_docker_enabled):
    if golden.needs_docker and not is_docker_enabled:
        pytest.skip("golden run needs --docker")

    result = run_agent(intent=golden.intent,
                       project_name=function_project.project_name,
                       api_url=function_project.api_url,
                       budget=golden.budget)

    assert result.plan_valid, result.plan_errors
    assert result.tool_calls_outside_allowlist == []
    assert set(result.completed_steps) >= set(golden.required_steps)
    assert result.cost_usd <= golden.budget.max_usd

    for name, value in golden.expected_outputs.items():
        assert json.loads(result.outputs[name]) == pytest.approx(value,
                                                                 rel=golden.tolerance)

Using real test fixtures rather than mocking the backing API matters more than it looks. A mock cannot confirm that the executor's field coercion matches a live schema, and field coercion is exactly the kind of thing that breaks silently on an upstream release.

Flaky fixtures teach people to ignore red builds

Symptom: the nightly suite fails intermittently on solver noise, and the team stops reading the results.

Cause: real solvers differ at the last decimal, and queue timing varies run to run.

Mitigation: assert with tolerances rather than equality, split the suite so deterministic evals block merges and golden runs page only on a trend, and share fixture setup so one slow provisioning step is not repeated per test.

LLM-as-judge, and how it rots

Use a judge only where no deterministic check exists, pin its model, and check it against a human-labelled holdout.

A judge is a model scoring another model's output against a rubric. It earns its place for genuinely subjective properties, such as whether a diagnosis explains the failure in a way an engineer can act on. It is the wrong tool for anything a schema check or a lookup can answer.

The judge is itself subject to every failure mode it is meant to catch, including drift.

Grader drift

Symptom: the escalation rate creeps upward over weeks with no code change.

Cause: the grader model moved behind a floating alias, or a prompt edit shifted the boundary between ambiguous and incorrect.

Mitigation: pin exact model IDs, never a floating alias. Keep a frozen labelled set and run it in CI on every prompt or model change, and alert on a shift in the verdict distribution rather than waiting for someone to notice the escalation rate.

Making the grader testable in isolation is worth the design effort. Bind it to a strict schema at temperature zero, returning a parsed object rather than free text. Then every production call logs a (query, evidence, verdict, reason) tuple, and those logs become next quarter's eval set. Hand-label a few hundred and you can measure precision and recall per class without running the rest of the pipeline.

Where the eval set comes from

Nobody has a labelled dataset on day one. You harvest it from production, and the harvesting has to be designed in before it can happen.

The usual failure is waiting until you need an eval set to start building one, at which point the only option is hand-writing synthetic cases that share none of production's weirdness. The fix is structural: make every judgement call log the tuple that would let you grade it later.

# Every grader call in production writes one row. This is next quarter's eval set.
(query_hash, failure_signature, evidence_id, verdict, reason, model, ts)

Hand-label a few hundred of those and you can measure precision and recall per verdict class without running the rest of the pipeline. That works because the grader was deliberately built to be testable in isolation: strict schema, temperature zero, a parsed object rather than free text.

Source of cases Good for Watch out for
Production logs, sampled Realistic distribution Over-represents the common case
Escalations and human overrides The hard cases, already flagged by a person Biased toward failure; keep successes too
Past incidents Regression protection on bugs you already paid for Small; each is worth keeping forever
Synthetic and adversarial Coverage of rare or hostile inputs Never a substitute for real distribution
Stratify deliberately. A set that is 90% easy cases reports a number that barely moves.

Two rules keep the set trustworthy. Freeze it and version it, because a set that drifts alongside the system measures nothing. Hold out a slice you never tune against, or you are fitting prompts to the eval rather than to the problem.

Offline, online, and what to gate a release on

Offline evals tell you whether to ship. Online metrics tell you whether shipping worked, and they disagree more often than people expect.
Offline Online
Runs against A frozen labelled set Live traffic
Answers "Is this change better on cases we understand?" "Is it better on the cases we have?"
Latency of signal Minutes Days
Blind spot Anything not in the set No ground truth; only proxies
Neither replaces the other. Gate merges on offline; judge success on online.

What gates a merge: deterministic unit evals at 100%, and component evals (grader precision, retrieval recall@k) at or above their thresholds against the frozen set. These run in minutes and block.

What does not gate a merge: golden end-to-end runs against real fixtures. Real solvers differ at the last decimal and queue timing varies, so these page on a trend rather than failing a build. An intermittent red build teaches people to ignore red builds, which costs more than the bug it was meant to catch.

Rolling out a prompt or model change follows the same shape as any risky deploy. Shadow the new version first, running it alongside production on real traffic without acting on its output, and compare verdict distributions. Then a percentage rollout keyed on tenant so one customer sees one consistent system rather than a coin flip per request. Watch unassisted completion rate and cost per successful outcome, not just the headline accuracy number.

Optimising a metric into a worse system

Symptom: escalation rate drops and everyone celebrates, then human-override rate climbs a month later.

Cause: the change made the system more willing to answer rather than more likely to be right. Escalation rate read alone rewards confidence.

Mitigation: never read escalation rate without grader precision beside it. A rising escalation rate where every escalation is a correct "I don't know" is a healthy system, and the pair distinguishes the two cases.

Observability: the trace is the eval you did not write

One run is one trace, with the workflow, each activity, and each model call as spans in the same tree.

Current OpenTelemetry GenAI conventions give the span attributes names worth using rather than inventing your own: gen_ai.provider.name, gen_ai.request.model, gen_ai.usage.input_tokens and .output_tokens, gen_ai.response.finish_reasons.

Prompt content stays out of the tracing backend. Store it externally, keyed by run and call ordinal, and put only a reference attribute on the span. Solver output and customer data do not belong in a telemetry system that has a different retention policy and a different access list.

Typed search attributes on the trace turn "show me every diverged run this week" into a query instead of a support ticket. Dashboards plot the five metrics above over time and version, and alerts fire on a validity drop, an escalation rise, or a cache-read ratio hitting zero, which is usually the first sign someone reordered a prompt.

Takeaways

  • Build the pyramid bottom-up. Deterministic checks at the base catch most regressions for milliseconds.
  • Split by determinism: deterministic evals block merges, golden runs page on a trend.
  • Assert with tolerances against real fixtures. A mock cannot confirm behaviour against a live schema.
  • Pin judge model IDs and check them against a frozen human-labelled holdout.
  • Log grader tuples in production; they become next quarter's eval set. Design that in before you need it.
  • Freeze and version the eval set, stratify it deliberately, and hold out a slice you never tune against.
  • Gate merges on offline evals; judge success on online metrics. Shadow first, then roll out by tenant.
  • Never read escalation rate without grader precision beside it.
  • Keep prompt content out of the tracing backend; store a reference.
