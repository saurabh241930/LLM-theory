Embedding Migration & Corpus Versioning

Changing the model under a live index, and keeping stale content from answering

Two upgrades that look similar and are not

A new embedding model invalidates every vector. A new corpus release invalidates the meaning of chunks whose vectors are still fine.
Embedding model change Corpus version change
What breaks Vectors are no longer comparable Content is superseded but still retrievable
Symptom Nonsense distances, recall collapses Confident answers for the wrong release
Errors? None None
Fix Dual-write migration with a model stamp Validity window plus a version predicate
Neither raises an exception, which is what makes both expensive to discover.

Why you cannot mix two embedding models in one index

Vectors from different models occupy different spaces. Distance between them is a number without meaning.

Two embedding models trained separately place "AMG solver diverged" in unrelated positions. Cosine distance between a vector from model A and one from model B is computable and meaningless, so a mixed index returns confidently wrong neighbours with no error at any layer.

Dimension count compounds it. Index implementations cap vector dimensions, and a model exceeding that cap cannot go into the same column at all.

Embedding-model upgrade forces a full re-embed

Symptom: a better embedding model looks like an unbounded migration nobody wants to start.

Cause: vectors from two models are not comparable in one index, and the dimension cap may block the new model from sharing the column.

Mitigation: store embedding_model on every row. Write to a new column, backfill off-peak, dual-read during cutover, then drop the old column. The risk is dimension mismatch and rebuild time, not the token bill.

The dual-write cutover

Five phases, each reversible, with no window where retrieval is broken.
flowchart TD P1["1. Add column + index
embedding_v2, model stamped"] --> P2["2. Dual-write
new ingests fill both"] P2 --> P3["3. Backfill off-peak
oldest first, rate-limited"] P3 --> P4["4. Dual-read + compare
shadow queries, measure recall"] P4 --> P5["5. Cut over, then drop v1"]
Phase Reads served by Rollback
1. Schema v1 Drop the column
2. Dual-write v1 Stop writing v2
3. Backfill v1 Pause; v1 untouched throughout
4. Dual-read v1, with v2 shadowed and compared Stop shadowing
5. Cut over v2 Flip back while v1 exists
v1 stays authoritative until measurements say otherwise.

Phase 4 is the one people skip, and it is the one that makes the decision defensible. Run the same queries against both columns and compare recall against a labelled set. "The new model is better" should be a measurement on your corpus, not the vendor's benchmark on someone else's.

The query-side predicate is what keeps a half-migrated index honest:

WHERE tenant_id IN ($5, '__shared__')
  AND embedding_model = $4        -- never mix vectors from two models
  AND valid_to IS NULL

Every index carrying vectors needs this, including the memory graph. Its nodes are entered by vector search, so an upgrade that skips them breaks precedent recall silently. See Agent Memory Systems.

Corpus versioning: enforce it three times

Stale-but-plausible content passes every surface check, so one guard is not enough.

Product documentation reissues per release. A page from an older release can be topically near-identical to a current failure, cite correctly, grade as relevant, and still be wrong. The remediation then consumes an approval and a long solve before failing.

  • As a pre-filter predicate, so off-version chunks never enter the candidate pool. Documentation with no version applies to all, expressed explicitly rather than as NULL ambiguity.
  • As a grader rule. A version mismatch alone downgrades correct to ambiguous, even when the content matches perfectly. The grader is told this directly.
  • As a visible citation field, so a human reviewing a proposal sees which release the evidence came from.

Retirement uses a validity window rather than a delete. Setting valid_to = now() on superseded chunks removes them from retrieval while keeping them for audit, which matters when somebody asks six months later why a run made a particular decision.

Index drift after a product release

Symptom: the week after a release, diagnoses cite the previous version and confidence drops, with nothing erroring.

Cause: docs are a versioned artefact but the index is not release-aware, so old chunks keep retrieving alongside new ones.

Mitigation: retire superseded chunks on ingest with valid_to, and alert on drift between the version retrieved and the version running.

Refresh cadence per source

Each source changes on someone else's schedule, and the ingest trigger should match it.
Source Trigger Why that trigger
Solver logs On failure, synchronously The log for this failure must be searchable before diagnosis runs
Product docs Per release, diffed by content hash Only changed pages need re-embedding
Skills On every git merge Small, and the source of truth is version control
Past runs On confirmed-green completion Write-back discipline gates entry
Synchronous ingest for logs is a correctness requirement, not a performance choice.

Diffing docs by content hash is what keeps a per-release re-index affordable. A release usually changes a small fraction of pages, and re-embedding only those turns a full rebuild into a modest incremental job.

Takeaways

  • Never mix vectors from two models in one index. Stamp embedding_model on every row and filter on it.
  • Migrate by dual-write: new column, backfill off-peak, dual-read and compare, cut over, drop.
  • Measure the new model's recall on your corpus before cutting over.
  • Enforce version three times: pre-filter predicate, grader rule, visible citation.
  • Retire with a validity window rather than a delete, so audit survives.
  • Match refresh cadence to each source. Logs ingest synchronously because diagnosis depends on them.
