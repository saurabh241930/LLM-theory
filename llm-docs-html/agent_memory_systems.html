Agent Memory Systems

Working state, durable memory, and the discipline that keeps memory honest

Three things get called memory

Conversation buffer, run state, and cross-run knowledge have different lifetimes, different stores, and different failure modes.
Kind Lifetime Where it lives Fails by
Working context One model call The prompt Growing until it crowds out the current task
Run state One run, hours to days Durable workflow history Lost on a crash if kept in process memory
Long-term memory Months, across runs and users A database, queried deliberately Accumulating confident nonsense
Most "agent memory" libraries solve the first and quietly ignore the third.

Conflating them produces predictable bugs. Treating run state as conversation means a worker restart loses the plan. Treating long-term memory as a conversation buffer means every past run gets stuffed into context whether or not it is relevant. Treating working context as durable means nothing survives the request.

Run state: the part people put in the wrong place

A run's status, plan, cursor and budget are not conversation. They are state, and they need to survive a process dying.

An ordinary Python process keeps its state in local variables and on the stack. Kill it and the state is gone; you rebuild from whatever you remembered to write to a database. Durable execution inverts that: the orchestrator is an ordinary function whose local variables survive a crash, because every decision it makes and every result it receives is recorded in an append-only history. A replacement worker replays that history through the same function and lands at exactly the point it left off.

class RunSolutionWorkflow:
    def __init__(self):
        self.status = "PLANNING"
        self.plan_ref: str | None = None      # object-storage URI, not the plan
        self.cursor = 0
        self.decision: ApprovalDecision | None = None
        self.budget: Budget | None = None

Those five attributes are the run's entire memory. No status column, no reconciler cron job, no separate accounting table for spend. The budget cannot be double-counted by a retry because the replay is deterministic, and it can be read live by a status query.

Note plan_ref rather than plan. A plan with many steps and assumptions can approach a payload limit when passed on every step transition. Storing a reference and loading the object when something genuinely needs it is the claim-check pattern, covered in Agentic Workflows.

Long-term memory as a graph, not a chat log

The useful cross-run question is "what fixed something like this before", which is a relationship lookup, not a similarity search over transcripts.

Storing past conversations and retrieving similar ones is the common design and a weak one. A transcript is mostly narration. What you want back is a structured fact: this failure signature, this remediation kind, this outcome.

erDiagram RUNS ||--o{ STEPS : contains STEPS ||--o{ FAILURES : raises FAILURES ||--o{ REMEDIATIONS : proposes REMEDIATIONS ||--o{ OUTCOMES : results_in FAILURES ||--o{ MEM_NODES : recorded_as MEM_NODES ||--o{ MEM_EDGES : connects

Two tables carry it. mem_nodes holds one row per failure signature, remediation kind, or skill tag, each with an embedding. mem_edges holds typed, weighted relationships between them: fixed_by, similar_to, cites.

WITH RECURSIVE hop(node_id, relation, depth, path) AS (
    SELECT n.node_id, NULL::text, 0, ARRAY[n.node_id]
    FROM   mem_nodes n
    WHERE  n.node_id = $1                    -- nearest failure-signature node
  UNION ALL
    SELECT e.dst_node_id, e.relation, h.depth + 1, h.path || e.dst_node_id
    FROM   hop h
    JOIN   mem_edges e ON e.src_node_id = h.node_id
    WHERE  h.depth < 2                       -- cap at two hops
      AND  NOT e.dst_node_id = ANY(h.path)   -- no cycles
)
SELECT n.node_id, n.node_type, h.relation, h.depth
FROM   hop h
JOIN   mem_nodes n ON n.node_id = h.node_id
WHERE  h.depth > 0
  AND  n.tenant_id = $2
ORDER  BY h.depth, h.node_id;

A bounded two-hop walk, one SQL round trip, zero LLM calls. This is the narrow case where a graph beats a flat index, and the reason is that the relationships are small, structured, durable, and written as a side effect of work that was happening anyway. See Graph RAG for when that stops being true.

Write-back discipline: how memory gets poisoned

The dangerous failure is not forgetting. It is remembering a coincidence as a lesson, then recommending it confidently for months.

The naive rule is to write back whenever a run succeeds after a remediation. That rule records coincidences. A retry happens to pass because an unrelated cluster queue cleared; the system records "lowering the Courant number fixed AMG divergence" and starts recommending it. Nothing about the row looks wrong afterward, which is what makes it hard to find.

Guard Rule Stops
Strict terminal success Write only when the retry reached terminal success Recording partial or ambiguous outcomes
Sole-change The remediation must be the only thing that changed Crediting a fix for someone else's change
Weight decay Edge weight decays when a reused fix stops working Stale advice outliving its usefulness
Human gate on novelty A remediation kind not seen before needs approval to enter memory A single bad run teaching the system a new bad habit
Four guards, each cheap, each catching a different way memory goes wrong.

Weight decay matters more than it looks. Without it, nothing ever leaves memory, and removing a bad row requires somebody to notice it is bad. Decay means a fix that stops working loses influence on its own.

Poisoned write-back memory

Symptom: a remediation marked successful because an unrelated change fixed the run, then recommended confidently later.

Cause: the write-back rule credited a coincidence.

Mitigation: strict terminal-success semantics plus the sole-change rule, weight decay on reuse failure, and human approval for novel fix kinds. All four are cheap; the bug is expensive and silent.

Embedding model change invalidates the memory index

Symptom: similar-failure recall stops surfacing precedent after an embedding upgrade, with no error.

Cause: vectors from two models are not comparable, and mixing them returns nonsense distances.

Mitigation: stamp embedding_model on every row, dual-write during cutover, and drop the old column once every reader has moved. See Embedding Migration & Versioning.

Retention, tenancy, and the right to delete

Memory is customer data. Every row carries a tenant, and stored text is the scrubbed version.

A memory graph built from real runs contains real customer detail: part numbers, file paths, hostnames, usernames. Two rules keep that from becoming a liability.

Every node and edge carries tenant_id, and every query filters on it in the SQL WHERE clause rather than in a prompt instruction. That makes deletion on request a normal delete rather than a research project, and it makes cross-tenant leakage a testable property. See Multi-Tenancy & Isolation.

Chunk text stored in memory is always the scrubbed version, never the raw log. Paths keep their basename and lose their directory; hostnames, usernames and licence-server names are stripped. A customer's internal detail should not end up in a shared index by way of "we remembered a fix".

Takeaways

  • Separate working context, run state, and long-term memory. They have different lifetimes and different failure modes.
  • Run state belongs in durable orchestrator state, not a process variable and not a status column.
  • Store structured outcomes, not transcripts. "What fixed something like this" is a relationship lookup.
  • Write-back needs four guards: terminal success, sole change, weight decay, and a human gate on novel fixes.
  • Every memory row carries a tenant, and stored text is scrubbed before it lands.
