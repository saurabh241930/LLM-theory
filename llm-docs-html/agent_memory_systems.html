Memory Systems

Three things get called memory

Separate them or get predictable bugs

Different lifetimes, different stores, different failure modes.

Most "agent memory" libraries solve the first and quietly ignore the third.

Conflate them and the bugs are predictable. Run state treated as conversation means a restart loses the plan. Long-term memory treated as a buffer means every past run gets stuffed into context.

Run state belongs in durable storage

Status, plan, cursor and budget are state, not conversation.
class RunSolutionWorkflow:
    def __init__(self):
        self.status = "PLANNING"
        self.plan_ref: str | None = None      # a URI, not the plan
        self.cursor = 0
        self.decision: ApprovalDecision | None = None
        self.budget: Budget | None = None

Five attributes are the run's entire memory. No status column, no reconciler, no separate spend table. Because replay is deterministic, the budget cannot be double-counted by a retry.

Note plan_ref rather than plan. A large plan passed on every step transition approaches the payload limit. See Durable Execution.

Long-term memory as a graph

"What fixed something like this?" is a relationship lookup, not a similarity search over transcripts.

A transcript is mostly narration. What you want back is a structured fact: this signature, this fix, this outcome.

erDiagram RUNS ||--o{ STEPS : contains STEPS ||--o{ FAILURES : raises FAILURES ||--o{ REMEDIATIONS : proposes REMEDIATIONS ||--o{ OUTCOMES : results_in FAILURES ||--o{ MEM_NODES : recorded_as MEM_NODES ||--o{ MEM_EDGES : connects

Two tables carry it. mem_nodes holds failure signatures, fix kinds and skill tags. mem_edges holds typed weighted relations: fixed_by, similar_to, cites.

WITH RECURSIVE hop(node_id, relation, depth, path) AS (
    SELECT n.node_id, NULL::text, 0, ARRAY[n.node_id]
    FROM   mem_nodes n WHERE n.node_id = $1
  UNION ALL
    SELECT e.dst_node_id, e.relation, h.depth + 1, h.path || e.dst_node_id
    FROM   hop h JOIN mem_edges e ON e.src_node_id = h.node_id
    WHERE  h.depth < 2                       -- cap at two hops
      AND  NOT e.dst_node_id = ANY(h.path)   -- no cycles
)
SELECT n.node_id, n.node_type, h.relation, h.depth
FROM   hop h JOIN mem_nodes n ON n.node_id = h.node_id
WHERE  h.depth > 0 AND n.tenant_id = $2
ORDER  BY h.depth;

One SQL round trip, zero LLM calls. Embeddings find the door; edges walk the building. See Graph RAG for when that stops being the right shape.

How memory gets poisoned

The dangerous failure is not forgetting. It is remembering a coincidence as a lesson.
flowchart TD R["Retry passes"] --> Q1{"Terminal success?"} Q1 -->|no| D["Do not write"] Q1 -->|yes| Q2{"Was the fix the
only change?"} Q2 -->|no| D Q2 -->|yes| Q3{"Novel fix kind?"} Q3 -->|yes| H["Human approval first"] Q3 -->|no| W["Write the edge"] W --> DEC["Weight decays if
reuse stops working"]

The naive rule writes back whenever a run succeeds after a fix. That records coincidences. A retry passes because an unrelated queue cleared, and the system learns the wrong lesson. Nothing about the row looks wrong afterward, which is what makes it hard to find.

Poisoned write-back

Symptom: a fix marked successful for an unrelated reason, recommended confidently for months.

Cause: the write-back rule credited a coincidence.

Mitigation: all four guards above. Weight decay matters most — without it nothing ever leaves memory unless somebody notices it is wrong.

Embedding change breaks the index

Symptom: recall stops surfacing precedent after an upgrade, with no error.

Cause: vectors from two models are not comparable.

Mitigation: stamp embedding_model per row, dual-write during cutover, drop the old column once every reader moves. See Embedding Migration.

Memory is customer data

Every row carries a tenant, and stored text is the scrubbed version.

A memory graph built from real runs contains part numbers, file paths, hostnames and usernames.

Every node and edge carries tenant_id, filtered in the SQL WHERE clause rather than a prompt instruction. That makes deletion an ordinary delete and cross-tenant leakage a testable property. See Multi-Tenancy & Isolation.

Stored chunk text is always scrubbed, never the raw log. A path keeps its basename and loses its directory.

Takeaways

  • Separate working context, run state and long-term memory.
  • Run state belongs in durable orchestrator state, not a process variable.
  • Store structured outcomes, not transcripts.
  • Write-back needs four guards: terminal success, sole change, weight decay, human gate on novel fixes.
  • Every row carries a tenant, and text is scrubbed before it lands.
