Durable Execution

When the run outlives the request

The problem

A four-hour solve, a day-long approval, and a worker restart all break an agent that keeps state in process memory.

The 600-second wait ceiling

Symptom: a prototype passes every test against a two-minute mock, then fails the day it meets a real six-hour job.

Cause: the wait helper is a blocking sleep loop inside one HTTP request, hard-capped at 600 s.

Mitigation: never wait inside a tool call. Poll from a durable timer, 30 s doubling to a 300 s cap with jitter.

How replay works

Your orchestration is an ordinary function whose local variables survive a crash.
flowchart TD W["Workflow function runs"] --> H["Every command and result

through the same function"] N --> A["Recorded awaits return
instantly with recorded answers"] A --> P["Lands exactly where it left off
cursor, budget, status intact"]

No status column. No reconciler cron job. The loop position and the budget are ordinary attributes that happen to be crash-proof.

An LLM call inside workflow code

Symptom: a run that worked on Monday produces a different plan, or a non-determinism error, after a routine deploy.

Cause: the model call was made from workflow code. A replay can return different text, and recovery depends on issuing the same commands every time.

Mitigation: every LLM call lives in an activity with a bounded retry policy. The workflow branches only on the typed objects those activities return.

Idempotency

A retry re-runs the whole function, including side effects the first attempt already committed.

Charged twice."] K -->|yes| OK["Returns recorded handle.
Resumes."] 
# Derived from identifiers the caller already has — never a fresh UUID.
key = f"{run_id}:{step.ordinal}:{step.transaction}"

def run_transaction(client, project, step, transaction, args, *, idempotency_key):
    if already_applied(idempotency_key):
        return load_handle(idempotency_key)      # resume, do not resubmit
    result = invoke(client, project, step, transaction, args)
    record(idempotency_key, result)
    return result

A UUID minted inside the activity is a different key every attempt and protects nothing.

A 30-second sleep and a 30-day sleep cost the same: nothing.

Human approval is a timer plus a signal. That is why a durable orchestrator handles it natively and a ReAct loop cannot.

Approval fatigue

Symptom: engineers approve without reading.

Cause: too many action classes trigger a gate.

Mitigation: gate on action class, not step count, and batch one approval per plan.

History growth

Approvals lost across continue-as-new

Symptom: a run that compacted during an open approval window never resumes.

Cause: continue-as-new starts a fresh execution. Anything not passed forward is gone, including the pending request ID.

Mitigation: carry the pending approval into the arguments and re-register the wait before doing anything else.

A code change breaks in-flight runs

Symptom: a run started before a deploy fails right after, with no change to its own state.

Cause: the new binary replays old history against changed code, and the emitted commands no longer match.

Mitigation: wrap every behaviour change in a versioning gate, and replay real production histories in CI before a risky deploy.

Takeaways

  • Move the wait out of the request. A six-hour sleep costs what a 30-second one costs.
  • Keep orchestration deterministic. Every LLM and HTTP call belongs in a retryable activity.
  • Derive idempotency keys from stable identifiers, and check the ledger before acting.
  • Approval is a timer plus a signal. Escalate once, then fail closed.
  • Pass references, not payloads, and compact history before it bites.
