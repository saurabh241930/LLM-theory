Structured Outputs & Guardrails

Constrained decoding, allow-lists, and gates the model cannot argue with

Structured outputs: removing a failure class rather than defending against it

Constrained decoding makes a token that would violate your schema impossible to emit, so "the model returned prose instead of JSON" stops being a thing that happens.

A language model is a text generator. Left alone, it answers a question about a plan with prose that contains JSON somewhere: maybe fenced in backticks, maybe not, maybe with a trailing sentence explaining its reasoning. Parsing that with a regular expression is the single most common source of silent failure in early agent systems. A stray comma, a fence the model forgot to close, an extra field it helpfully added, and your parser either throws or succeeds on garbage.

Structured outputs remove that class structurally. You hand the provider a JSON Schema, generated from your own model definition, and decoding itself is constrained so a token that would violate the schema cannot be emitted. What comes back is guaranteed to be syntactically valid JSON matching that shape, every time.

resp = await claude.messages.create(
    model="claude-opus-5",
    system=system,
    messages=[{"role": "user", "content": req.intent}],
    output_config={"format": {"type": "json_schema",
                              "schema": Plan.model_json_schema()}},
    max_tokens=8000,
)
plan = Plan.model_validate_json(resp.content[0].text)
validate_plan(plan, req.solution_id)        # semantics, separately
Structural validity is necessary, not sufficient. A schema-valid Plan can still name a step that does not exist or write a field in the wrong units. The schema constrains shape, not membership.

The gap the schema leaves open

A str field compiles to "any string", so nothing stops a plausible-sounding invention.
Hallucinated step names

Symptom: the first activity fails immediately with unknown step 'meshing', on a solution whose step is clearly named mesh.

Cause: step: str compiles to a JSON Schema type of "string". Nothing in constrained decoding stops the model from generating a plausible name that never appeared in its prompt, especially under a long context or a paraphrased intent.

Mitigation: cross-check every step and transaction against the real schema before anything runs, and put the valid names in the error. That error becomes the feedback for the next attempt, so the model corrects itself in one replan rather than looping.

def validate_plan(plan: Plan, solution_id: str) -> None:
    schema = SolutionSchema.for_solution(solution_id)
    order = {name: i for i, name in enumerate(schema.dag.toplogical_sort())}
    produced: set[str] = set()

    for s in plan.steps:
        if s.step not in schema.steps:
            raise ValueError(f"unknown step {s.step!r}; known: {sorted(schema.steps)}")
        if s.transaction not in schema.steps[s.step].transaction_names:
            raise ValueError(f"unknown transaction {s.step}.{s.transaction!r}")
        if not is_allowed(solution_id, s.step, s.transaction):
            raise ValueError(f"{s.step}.{s.transaction} is not allow-listed for this role")
        for field in s.inputs:
            if (s.step, field) not in order and (s.step, field) not in produced:
                raise ValueError(f"{s.step}.{field} has no upstream producer in this plan")
        produced.update((s.step, name) for name in s.expected_outputs)

Four checks, none of them touching the network, all running against structures loaded at worker start. A plan earns the right to spend a solver-hour by passing them. A validation failure is not an error; it is feedback for the next planning attempt.

Structured-output schemas reject some constraints outright. Numeric bounds, string length limits, and recursive types are frequently not representable in the constrained grammar providers support. Keep those checks in validator methods on your model rather than in field constraints, and the schema stays acceptable to the API.

Closed enums: the backstop that holds under attack

If the model's action must be one of six values, no prompt injection can invent a seventh.
class RemediationKind(StrEnum):
    RETRY           = "retry"
    ADJUST_FIELD    = "adjust_field"
    RERUN_UPSTREAM  = "rerun_upstream"
    SWITCH_SKILL    = "switch_skill"
    ESCALATE        = "escalate"
    ABORT           = "abort"

This is the most valuable line of defence in the whole system, and it is six lines of Python. A compromised diagnosis, whatever a poisoned solver log talked the model into believing, cannot name an action outside this set. There is no delete_project to reach for, because the type does not admit one.

An enum also fails loudly on a typo, unlike a plain string, and comparisons against it are deterministic and replay-safe in a way that matching on model prose never is.

Guardrails: deterministic code, not a second opinion

An allow-list, a budget, and an approval gate keyed to an action class. All three run whether or not the model behaves.

The tempting design is to ask a second model whether the first model's action is safe. That doubles cost, adds latency, and gives you two non-deterministic components instead of one. Guardrails worth the name are ordinary code.

Action class Gate Approver Timeout default
read_only None, always executes — —
mutating Auto-executes if confidence ≥ 0.75 and kind is allow-listed Engineer who started the run 4 hours
expensive Approval always Engineer, or team lead above a cost threshold 4 hours, then escalate
destructive Approval always Team lead 2 hours, then escalate
ip_sensitive Approval always Platform admin 1 hour, then escalate
The gate depends on the class of action, never on which specific step is running.

Gating on action class rather than on step count is what keeps approval meaningful. Gate everything and reviewers approve without reading, which protects nothing. See Agentic Workflows for the durable-wait mechanics.

The default posture is deny. A transaction absent from the allow-list is never offered to the Planner as an option in the first place, which is a cheaper guarantee than trusting the model to decline it on its own.

Validating evidence IDs

One more check runs on every model output before the allow-list: the evidence list in a proposed action is validated server-side against the IDs retrieval actually returned. An invented citation is rejected rather than displayed. Without this, a confident fabricated reference is indistinguishable from a real one in the UI.

Layering the defences

Each layer catches a different failure, and the cheapest ones run first.
Layer Catches Cost
Constrained decoding Malformed or non-JSON output Free, provider-side
Pydantic model validation Wrong types, missing fields, unknown fields Microseconds
Semantic validation against ground truth Invented step names, impossible order, missing inputs Microseconds, in-memory lookup
Allow-list Actions this role may never take A set membership test
Evidence-ID validation Invented citations A set membership test
Budget check Spend beyond what the user authorised Three comparisons
Approval gate Everything above, judged by a human Minutes to hours of wall clock
A microsecond check ahead of a solver-hour is never a close call.

Takeaways

  • Constrained decoding removes malformed output as a category. It does not make the content correct.
  • Validate semantics against ground truth the system owns, and put the valid options in the error so it becomes usable feedback.
  • A closed enum is the cheapest strong defence in an agent. Injected text cannot name an action the type does not admit.
  • Gate on action class, not step count, or approval becomes a reflex.
  • Default to deny: an action absent from the allow-list is never offered as an option.
