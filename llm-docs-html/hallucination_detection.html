Hallucinations in Production

Six failure classes, and the structural fix for each

"Hallucination" names six different bugs

Treating them as one problem leads to one blunt mitigation, usually a confidence score, which fixes none of them well.

The word covers a model inventing a citation, misreading a number, naming a function that does not exist, and confidently answering from an empty retrieval. Those have different causes, appear at different points in the pipeline, and have different fixes. Most are structural: you make the failure impossible rather than detecting it afterwards.

Stale-but-plausible Correct answer for last year's version Version as filter predicate and grader rule Near zero
Five of six are prevented by code. Only the last two need a model in the loop.

Class 1-2: shape and membership are different guarantees

Constrained decoding guarantees valid JSON. It says nothing about whether the strings inside mean anything.

Structured outputs remove malformed output entirely: decoding is constrained so a token violating the schema cannot be emitted. That kills the whole regex-parsing failure class.

It does not touch the next one. A field declared step: str compiles to a JSON Schema type of "string", and nothing stops a plausible-sounding invention.

Hallucinated step names

Symptom: the first activity fails with unknown step 'meshing' on a solution whose step is named mesh.

Cause: structured outputs constrain shape, not membership. Long context or a paraphrased intent makes a near-miss name more likely.

Mitigation: cross-check every identifier against the real schema before anything runs, and put the valid names in the error text. That error becomes the feedback for the next attempt, so the model self-corrects in one replan rather than looping.

The general rule: whenever the system owns ground truth, check against it rather than hoping. A microsecond lookup ahead of a solver-hour is never a close call. See Structured Outputs & Guardrails.

Class 3-4: closed sets beat detection

If the output must be one of six enum values, no amount of hallucination or injection produces a seventh.
class RemediationKind(StrEnum):
    RETRY = "retry"
    ADJUST_FIELD = "adjust_field"
    RERUN_UPSTREAM = "rerun_upstream"
    SWITCH_SKILL = "switch_skill"
    ESCALATE = "escalate"
    ABORT = "abort"

There is no delete_project for a confused or manipulated model to reach for, because the type does not admit one. This is the cheapest strong guarantee in the whole system.

Invented citations get the same treatment. A proposed action carries an evidence list, and those IDs are validated server-side against the IDs retrieval actually returned. An invented reference is rejected rather than rendered. Without that check, a fabricated citation is indistinguishable from a real one in the UI, which is the version of this bug that damages trust hardest.

Class 5: the empty-retrieval failure

Nearest-neighbour search always returns k results, including when nothing relevant exists.

This is the most under-appreciated hallucination source in RAG, because the retrieval looks like it worked. Ask about an HPS queue timeout with nothing about HPS indexed, and vector search returns the k least-unrelated chunks, probably about meshing. An ungoverned model builds a confident answer from them.

Plain RAG has no way to say "nothing here". Corrective grading gives it one: a grader scores each candidate correct, ambiguous, or incorrect before anything reaches the generation step, and an empty kept-set returns a typed escalation.

if not kept:
    return RemediationAction(kind=RemediationKind.ESCALATE,
                             reason="no evidence graded relevant after retrieval",
                             evidence=[], confidence=0.0, requires_approval=True)
Why three verdicts, not two

A binary relevant/irrelevant judgement hinges on the grader being right at exactly one threshold, and graders are not that well calibrated. Three grades let the upper threshold clear an answer, the lower one discard it, and the middle absorb genuine uncertainty.

ambiguous is the honest label for most real evidence. A page describing the same failure family, for a different product version, is neither correct nor irrelevant.

Class 6: right answer, wrong version

The hardest class, because every surface-level check passes.

A 2023R1 documentation page can be topically near-identical to a 2025R2 failure, cite correctly, grade as relevant, and still be wrong. Nothing about the output looks broken. The remediation runs, consumes an approval and an eight-hour solve, and fails.

Version correctness gets enforced three separate times, because one check is not enough:

  • As a pre-filter predicate, so off-version chunks never enter the candidate pool.
  • As a grader rule: a version mismatch alone downgrades correct to ambiguous, even when the content matches perfectly.
  • As a visible citation field, so a human reviewing the proposal sees which version the evidence came from.
Index drift after a product release

Symptom: the week after a release, diagnoses cite the previous version and confidence drops, with nothing erroring.

Cause: docs are a versioned artefact but the index is not release-aware, so old chunks keep retrieving.

Mitigation: retire superseded chunks with valid_to = now() on ingest, and alert on drift between the version retrieved and the version running.

Where scoring still earns its place

Confidence scores are for routing, not for catching the classes above.

A confidence number is a poor detector and a decent router. In the running system it decides whether an action executes automatically or waits for a human: a proposal auto-applies only when confidence is at or above 0.75 and the action kind is on the auto-safe list. Everything else routes to approval regardless of how confident the model claims to be.

That is the right use. The score never decides whether the content is true; it decides who looks at it before it runs.

For measuring the problem rather than preventing it, the eval pyramid gives numbers that move: grader precision against a frozen labelled set, unassisted-completion rate, and escalation rate over time. A rising escalation rate where every escalation is a correct "I don't know" is a healthy system. See Evaluating Agent Systems.

Takeaways

  • Name the class before reaching for a mitigation. Five of six are prevented by code, not detected by a model.
  • Constrained decoding kills malformed output. It does nothing about invented identifiers.
  • Closed enums and allow-lists make invented actions unrepresentable, which also blocks injection.
  • Validate citation IDs against what retrieval actually returned.
  • Make "found nothing" a typed return value, or the model will fill the gap.
  • Enforce version three times: filter, grader rule, visible citation.
