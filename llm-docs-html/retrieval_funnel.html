The Retrieval Funnel

Filter, hybrid search, fusion, rerank, grade, with candidate counts and per-stage cost

The organising principle

Each stage costs roughly 10-100x more per candidate than the one before, so it must see 10-100x fewer candidates. Everything else follows from that.

Why filter first

Metadata filtering is free, and it is a correctness boundary rather than an optimisation.

Filtering on tenant, solver and version comes first because a 2025R2 run must never see 2023R1 documentation, and one tenant must never see another's logs. Those are correctness properties, not performance tuning. Filtering first also prices every later stage against 8,000 candidates rather than 120,000.

Approximate indexes filter after the scan

Symptom: a selective filter returns 4 rows when you asked for 40, and nobody notices because 4 results still look like results.

Cause: HNSW and similar approximate indexes apply a predicate after the vector scan. With a search breadth of 40 and a predicate matching 10% of rows, roughly 4 survive. This breaks the naive reading of "filter first", which is a logical ordering, not automatically the physical one.

Mitigation: partial indexes for the handful of high-cardinality values, partitioning by tenant for large tenants, and an iterative-scan fallback bounded by a maximum tuple count.

Why keyword search is not optional

Engineers write tokens that carry no semantics, and an embedding model has no reason to place "217" near "217".

A failure signature contains things like mapdl.err, SIGSEGV, and Error code 217. Embeddings encode meaning, and these strings have none. Exact-match retrieval finds them reliably; vector search may not.

The opposite case is equally real. "Solution failed to converge" and "solver exited with code 217" describe the same event with almost no shared words, and only embeddings connect them. Neither method is strictly better, which is why both run.

WITH filtered AS (
    SELECT chunk_id, content, uri, content_tsv, embedding
    FROM   doc_chunks
    WHERE  tenant_id IN ($5, '__shared__')
      AND  solver = $2
      AND  (solver_version = $3 OR solver_version IS NULL)
      AND  embedding_model = $4
      AND  valid_to IS NULL
), kw AS (
    SELECT chunk_id,
           RANK() OVER (ORDER BY ts_rank_cd(content_tsv, q) DESC) AS rank
    FROM   filtered, websearch_to_tsquery('simple', $6) q
    WHERE  content_tsv @@ q
    LIMIT  100
), vec AS (
    SELECT chunk_id,
           RANK() OVER (ORDER BY embedding <=> $1::vector) AS rank
    FROM   filtered
    ORDER  BY embedding <=> $1::vector
    LIMIT  100
)
SELECT f.chunk_id, f.uri, f.content,
       COALESCE(1.0 / (60 + kw.rank), 0.0) +
       COALESCE(1.0 / (60 + vec.rank), 0.0) AS rrf_score
FROM   kw FULL OUTER JOIN vec USING (chunk_id)
JOIN   filtered f USING (chunk_id)
ORDER  BY rrf_score DESC
LIMIT  50;
'simple' rather than 'english' is deliberate. The English stemmer mangles identifiers like mapdl.err, so error-code search needs the unstemmed dictionary.

Both branches filter inside the same CTE, so the isolation boundary cannot be bypassed by fusing afterwards. Wall-clock cost is the larger of the two branches, not the sum, because they run against the same pre-filtered set in one round trip.

Why fuse before reranking

Reciprocal rank fusion produces one candidate pool from two lists that overlap unpredictably, so you rerank once instead of twice.

RRF combines two ranked lists using ranks only, never raw scores: score = Σ 1 / (k + rank) with k = 60 conventionally. Using ranks sidesteps the problem that a text-search score and a cosine distance are not comparable quantities and have no principled normalisation between them.

Reranking each list separately and fusing afterwards would double the rerank spend on partially overlapping sets, then throw away the cross-encoder's actual scores in favour of rank positions. Fuse first, rerank once.

Why rerank before the LLM grades, and when to drop the reranker

A cross-encoder scores candidates comparably against each other; the grader answers a binary question about one candidate in isolation and cannot rank at all.

The grader sees a query and one excerpt and returns a verdict. It has no view of the other 49 candidates, so it cannot say which is best. A cross-encoder reads query and document jointly and produces comparable scores across candidates, which is exactly the "pick the best 8 of 50" problem.

Cost makes the same argument. Grading all 50 directly instead of 8 costs roughly five times the tokens and needs 50 concurrent calls, which is where a rate limit bites.

The grader still runs afterwards, because it answers something no cross-encoder knows: a 2023R1 page can be topically near-identical to a 2025R2 failure and still be the wrong answer. A version mismatch downgrades a verdict from correct to ambiguous.

Situation Rerank? Reason
Pool > 3x final top-k Yes There is real ordering left to buy
Log chunks scoped to one run and step (20-30 candidates for a top-8) No Pre-filter already narrowed to near the answer width
Skills, a few dozen after the solver filter No Same reason; skip the hop
Product docs, thousands after filtering Always Ordering is the whole problem
Rule of thumb: rerank only when the pre-filtered pool exceeds ~3x the final top-k.
Rerank latency spikes

Symptom: p99 retrieval latency jumps to 3 seconds while p50 is unchanged.

Cause: the reranker is a third-party HTTP call in a hot loop, and oversized documents auto-chunk into multiple inferences invisibly.

Mitigation: a hard client timeout falling through to plain fusion ordering, since worse order beats no answer. Keep chunks under the auto-chunking threshold and cache by query hash, document IDs and model.

Where the caching actually helps

Precomputing at ingest beats caching at query time, and the grader's prompt is too short to cache.

Three layers do most of the remaining work. Computing contextualised chunks once at ingest rather than per query is the largest lever in absolute dollars. Prompt caching on the final assembly call's stable prefix pays back after a couple of reads inside the cache window.

The grader is the interesting case. Its prompt is a few hundred tokens, well under the minimum cacheable prefix on a small model, so prompt caching does nothing. Cache grader verdicts instead, keyed by query hash, evidence ID and model. See Model Routing & Cost Engineering.

Takeaways

  • Order stages by cost per candidate. Each stage should see 10-100x fewer candidates than the one before.
  • Filter first for correctness, not speed, and know that approximate indexes apply predicates after the scan.
  • Run keyword and vector together. Error codes have no semantics; paraphrases have no shared words.
  • Fuse with RRF before reranking so you pay the expensive stage once.
  • Drop the reranker when the pre-filtered pool is already near the answer width, roughly 3x top-k.
