Multi-Tenancy & Data Isolation

Predicates, partial indexes, and the test that proves it

Why this is an agent problem and not just a database one

Retrieval hands the model text from a shared index. One missing predicate and another customer's data is in your prompt, with no error and no log line.

A conventional application leaks tenant data through a bug in a query. An agent can leak it through a bug in a query and through the model summarising what it retrieved, so the leak arrives as fluent prose rather than as a row in a table. Nothing about the output looks wrong.

The control has to be a predicate in the SQL. A prompt instruction like "only consider tenant A's documents" is a request, it fails silently under prompt injection, and it leaves no audit trail.

Tenant leakage from a missing filter

Symptom: one tenant's engineer sees a chunk containing another tenant's part number.

Cause: a query builder omitted the tenant predicate, or a row landed with a NULL tenant and matched nothing, which in SQL means it also failed to be excluded by a naive check.

Mitigation: make the column NOT NULL with an explicit '__shared__' sentinel for genuinely shared content, add row-level security so the predicate cannot be forgotten, and assert zero cross-hits on a two-tenant fixture in CI.

The shape of a correct query

Filter inside every branch of a hybrid query, before fusion, so the boundary cannot be bypassed by joining afterwards.
WITH filtered AS (
    SELECT chunk_id, content, uri, content_tsv, embedding
    FROM   doc_chunks
    WHERE  tenant_id IN ($5, '__shared__')      -- the isolation boundary
      AND  solver = $2
      AND  (solver_version = $3 OR solver_version IS NULL)
      AND  embedding_model = $4
      AND  valid_to IS NULL
), kw AS (
    SELECT chunk_id, RANK() OVER (...) AS rank
    FROM   filtered, websearch_to_tsquery('simple', $6) q
    WHERE  content_tsv @@ q LIMIT 100
), vec AS (
    SELECT chunk_id, RANK() OVER (...) AS rank
    FROM   filtered ORDER BY embedding <=> $1::vector LIMIT 100
)
SELECT ... FROM kw FULL OUTER JOIN vec USING (chunk_id)
JOIN filtered f USING (chunk_id) ORDER BY rrf_score DESC LIMIT 50;

Both branches read from the same filtered CTE. A version that filtered only the vector branch would leak through keyword search, and a version that filtered after fusion would have already scanned rows it should never have touched.

The '__shared__' sentinel carries its weight. Product documentation is genuinely shared across tenants, and without an explicit value for that, the tempting implementation is a NULL meaning "applies to everyone". NULL comparisons in SQL are a reliable source of exactly this bug, so the sentinel makes the shared case explicit and lets the column be NOT NULL.

The index problem nobody warns you about

Approximate vector indexes apply the filter after the scan, so a selective predicate silently starves the result set.

"Filter first" is a logical ordering. The physical plan for an approximate nearest-neighbour index is usually the opposite: scan the index for the nearest candidates, then apply the predicate to what came back.

Search breadth Predicate selectivity Rows requested Rows actually returned
40 10% match 40 ~4
100 10% match 40 ~10
40 1% match (small tenant) 40 ~0
Post-filter starvation. Nothing errors; the answer is just thinner than you asked for.

Three fixes, matched to tenant size:

  • Partial indexes for a handful of high-value discriminating values, so the index itself only contains matching rows.
  • Partitioning by tenant for large tenants, which makes their queries scan only their own partition.
  • Iterative scan as a bounded fallback for the long tail, capped by a maximum tuple count so a pathological query cannot become a table scan.

The general rule: measure the returned row count against the requested count in production, per tenant. A small tenant getting four results where a large one gets forty is the signature, and it is invisible from application logs.

Isolation beyond retrieval

Every store the agent writes to inherits the same requirement, including the ones that feel like internal plumbing.
Store Isolation control Easy to forget because
Document chunks Tenant predicate in the CTE, row-level security —
Memory graph Tenant filter at every level of the recursion Filtering entry feels sufficient; hop two crosses the line
Object storage Prefix per tenant, scoped credentials URIs get passed around as opaque strings
Traces Tenant as a span attribute; prompts stored by reference Telemetry has a different access list
Eval fixtures Synthetic tenants only Real failures make convenient test data
The recursive walk and the trace backend are where this usually breaks.

The memory graph is the sharpest case. A recursive traversal that filters on tenant at entry and not inside the recursion will happily walk an edge into another tenant's subgraph on hop two. See Agent Memory Systems.

Proving it, rather than believing it

Zero cross-tenant rows is a testable property, and the test belongs in CI.
  • Two-tenant fixture. Seed distinctive content for tenant A and tenant B. Query as A using B's exact identifiers. Assert zero hits. Run it on every commit.
  • Fuzz the query surface. Generate queries from B's corpus and issue them as A. The distinctive-token approach catches the obvious break; fuzzing catches the partial one.
  • Assert the row count. A test that passes because retrieval returned nothing at all is not evidence of isolation. Check that A gets A's rows and none of B's.
  • Test deletion. Delete tenant B and assert nothing of B's survives anywhere, including the memory graph, object storage and traces.

Deletion is worth calling out. Every node, edge and chunk carrying a tenant ID is what makes a deletion request an ordinary delete rather than a research project. A memory graph built without that column is a compliance problem discovered under time pressure.

Takeaways

  • Isolation is a SQL predicate. A prompt instruction is not a control and leaves no audit trail.
  • Filter inside every branch of a hybrid query, before fusion.
  • Make the tenant column NOT NULL with an explicit shared sentinel; NULL is where this bug lives.
  • Approximate indexes post-filter. Watch returned-vs-requested row counts per tenant.
  • Filter at every level of a recursive traversal, not only at entry.
  • Assert zero cross-hits on a two-tenant fixture in CI, and check that the right rows still come back.
