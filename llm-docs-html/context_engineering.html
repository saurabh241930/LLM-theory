Context Engineering

What fills the window, in what order, at what cost

A production prompt is assembled, not written

By the time the request leaves your process, a human wrote maybe 15% of the tokens in it.
flowchart LR A["Instructions
you wrote"] --> P["The request"] B["Tool schemas
generated from code"] --> P C["Resources

So the useful questions are structural. What is stable enough to cache? What gets cut first when the window fills? Which parts are untrusted? What does each block cost, times a million calls a month?

Order by volatility

Stable blocks first, volatile last. Not by what feels important.
flowchart TD subgraph W["❌ By importance"] W1["retrieved evidence"] --> W2["instructions"] --> W3["tool schemas"] W3 --> W4["cache hit rate 0%
full price every call"] end subgraph R["✅ By volatility"] R1["instructions"] --> R2["tool schemas"] --> R3["resources"] --> R4["skill body"] --> R5["retrieved evidence"] R5 --> R6["everything above cached"] end
Layer Size Cacheable?
Instructions 300-2,000 Yes
Tool schemas 50-200 per tool Until you ship a change
Resources 500-4,000 Per solution
Skill descriptors ~100 each, always present Yes
Skill body 500-3,000, on a trigger No — place late
Retrieved evidence 1,000-10,000 Never — place last

Prefix caching keys on an exact byte-for-byte prefix. One retrieved chunk placed high invalidates everything after it.

Progressive disclosure

Keep a one-line descriptor of everything. Load the body only on a match.
flowchart LR subgraph A["Paste all 50"] A1["~75,000 tokens
~2% relevant"] end subgraph B["Disclose progressively"] B1["50 descriptors
~5,000"] --> B2["+1 body on match
~1,500"] end A1 -.->|"15x"| B1

The registry is what you pay for. The bodies are free until read. The same shape works for tool definitions, examples, and docs: keep an index, fetch the entry. See Agent Skills.

Context rot

More window is not more understanding. Two separate problems get conflated.

Fix What it does
Pass references A log is a URI and a hash, not 84,000 lines
Compact on a threshold Summarise, restart with fresh history plus the summary
Scope retrieval hard Filtering to one run and step leaves 20-30 candidates, not thousands
A payload too big for history

Symptom: a run with many replans throws payload-size warnings before any solver has run.

Cause: the full plan is passed as an activity argument on every step transition.

Mitigation: write it to object storage once, pass an ID and a short summary. Anything needing the full object calls a tiny load activity.

Trusted and untrusted regions

Context is not one uniform block. Some of it an attacker may have written.
flowchart TD Y["Instructions · tool schemas · resources
your team wrote these"] --> CTX["Context window"] N["Solver logs · scraped docs · past-run notes · uploads
someone else shaped these"] -->|"delimited, labelled"| CTX CTX --> OUT["Model output"] OUT --> ENUM["Bound to a closed enum
injected text cannot name
an action that does not exist"]

The policy line in the prompt is a filter, and filters leak. The guarantee is downstream: if the output binds to six enum values, a compromised model cannot produce a seventh. See Prompt Injection Defence.

Takeaways

  • Order by volatility so the prefix cache can hold the stable part.
  • Progressive disclosure turns fifty playbooks into a 5,000-token registry.
  • Pass references instead of payloads.
  • Compact history before it becomes the bottleneck.
  • Mark untrusted regions, and back the marking with a closed enum.
