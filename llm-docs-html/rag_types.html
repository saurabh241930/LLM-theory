Evolution of RAG Systems

The Architectural Journey from Naive Retrieval to Autonomous Agents

RAG is a spectrum, not one architecture. Each rung below adds a capability the rung beneath it lacks, and charges for it in LLM calls per query. Buy a rung only when the one below actually fails on your data.

This page is the map. Each stage links to its own deep dive.

Stage What it adds LLM calls per query Use when
1. Naive Retrieval before generation 1 The answer sits in one passage
2. Advanced Query rewriting, hybrid search, reranking 1-2 Retrieval finds the wrong passage
3. Corrective A grader between retrieve and generate ~3 batched You need the system to refuse to answer
4. Graph Traversal by relationship instead of similarity 1 SQL walk, 0 LLM when scoped Questions traverse relationships
5. Agentic Model picks the source, query, and when to stop Up to 9, capped in code Sources are heterogeneous and not interchangeable
The ladder, priced. Stage 4 is not strictly above stage 3; it answers a different shape of question.
Stage 1: Naive RAG

The "Search and Stuff" Baseline

The standard linear pipeline where a query is converted to a vector, the top-K chunks are retrieved, and they are "stuffed" into the LLM prompt.

graph LR Q[User Query] --> E[Embedder] E --> V[(Vector DB)] V --> K[Top-K Chunks] K --> LLM[LLM Generation]
✅ Benefit: Extremely low latency and simple implementation.
❌ Limit: Cannot say "nothing here". Nearest-neighbour search always returns k results, even when nothing relevant exists.

That last limit is the one that bites in production. Ask about a topic that was never indexed and you get the k least-unrelated chunks, from which an ungoverned model builds a confident wrong answer. Stage 3 exists to fix exactly this.

Stage 2: Advanced RAG

Pre-Retrieval & Post-Retrieval Optimization

Adds intelligence to the pipeline via query expansion (HyDE) and reranking (cross-encoders) so only gold-standard context reaches the LLM.

graph TD Q[Query] --> TRAN[Translation: HyDE/Rewrite] TRAN --> RET[Retrieval: Vector + Keyword] RET --> RANK[Post-Retrieval: Rerank/Refine] RANK --> GEN[LLM Generation]

The organising principle is cost per candidate. Each stage costs roughly 10-100x more per candidate than the one before, so it must see 10-100x fewer. A real funnel runs 120,000 candidates down to 5 for about $0.046: metadata filter, then BM25 and vector in parallel, then rank fusion, then a cross-encoder, then an LLM grade.

✅ Benefit: Large accuracy gain for near-zero added cost in the first three stages.
❌ Limit: Reranking buys nothing when the pre-filtered pool is already within ~3x your final top-k.

Stage 3: Corrective RAG (CRAG)

Grading Evidence Before Generating

A grader sits between retrieval and generation and scores each candidate before anything reaches the answer step. This is the rung that gives a RAG system the ability to refuse.

graph TD Q[Query] --> RET[Retrieve top-k] RET --> G[Grade each candidate] G -- correct --> GEN[Generate with citations] G -- ambiguous --> REF[Refine or rewrite query] G -- incorrect --> DROP[Discard] REF --> RET DROP --> NONE[Return: no relevant evidence]

Three verdicts rather than two, because a binary relevant/irrelevant call hinges entirely on the grader being right at one threshold, and graders are not that well calibrated. Ambiguous is the honest label for most real evidence: a document describing the same problem for a different product version is neither correct nor irrelevant.

✅ Benefit: A bad retrieval never becomes a confident wrong answer. "Found nothing" becomes a real return value.
❌ Limit: The grader is a model too, so it drifts. Pin its exact model ID and check it against a frozen labelled set.

Stage 4: Graph RAG

Traversal Instead of Similarity

Replaces the flat chunk index with an entity graph, so a query walks relationships rather than ranking by similarity. It answers questions whose answer spans several documents, where no single chunk contains the connection.

graph LR Q[Query] --> ENT[Vector search:
find entry node] ENT --> HOP[Walk edges,
capped at 2 hops] HOP --> CTX[Related entities
+ relationships] CTX --> LLM[LLM Generation]

Two questions decide whether it is worth it. Do your queries traverse relationships? "What fixed something like this before" is a walk; "what does error 217 mean" is a lookup, and a graph adds nothing. How fast does the index go stale? Full Graph RAG's index is LLM-built, so a corpus that reissues on a release cadence pays that construction bill again every release.

The cheap version is often the right one: a small graph written as a side effect of work already happening, queried by a bounded recursive SQL walk in the database you already run. Zero LLM calls, nothing to rebuild, and no second system where a tenant filter can be forgotten.

✅ Benefit: Answers multi-hop relationship questions vector search cannot reach.
❌ Limit: A dedicated graph database is real operational overhead. Earn it before adopting it.

Stage 5: Agentic RAG

Autonomous Decision Loops

No longer a fixed pipeline. The model chooses which source to consult, what to ask it, and when the evidence is sufficient. Choosing the source is the judgement.

graph TD T[Failure or task] --> AG[Choose tool and query] AG --> SRC{Which source?} SRC --> L[Logs: what happened] SRC --> D[Docs: what it means] SRC --> S[Skills: what to do] SRC --> P[Past runs: what worked] L --> EV[Grade the batch] D --> EV S --> EV P --> EV EV -- "3+ correct, or no new evidence, or iter 4" --> ANS[Typed action] EV -- "budget remains" --> AG

Use it when sources are genuinely not interchangeable. A licence failure needs the docs and the log; a solver divergence needs the log and the playbook; a serialization bug is answered by past runs alone. Any fixed order guesses wrong about half the time, which is what makes the choice worth an LLM call. With one corpus, a fixed pipeline is cheaper and more predictable.

✅ Benefit: Handles heterogeneous, unreliable sources that no fixed pipeline orders correctly.
❌ Limit: Highest cost, and an unbounded loop is the most common production failure. The cap belongs in code, not in a prompt.

Expert Interview: Senior RAG Design

Q: When is Naive RAG "enough" for a production app?
When the data is homogeneous (all one-page FAQs) and queries have high keyword overlap with the content. For engineers searching internal documentation, naive RAG with good chunking often outperforms complex agents that overthink simple retrievals. Spend your effort on chunking before you spend it on orchestration.
Q: What is the "silver bullet" for RAG accuracy?
Reranking, with one caveat. A cross-encoder gives the highest accuracy return for the implementation effort, but only where the pre-filtered pool exceeds roughly 3x your final top-k. Below that it buys almost no new ordering and still costs you its latency and rate limit. Measure the pool size before adopting it as a default.
Q: What does Corrective RAG actually add over Advanced RAG?
The ability to return nothing. Advanced RAG improves which chunks you retrieve; it never questions whether they answer the question. CRAG inserts a grader that can discard the whole slate, which converts the most dangerous RAG failure, a confident answer built from irrelevant chunks, into an explicit "no relevant evidence".
Q: Is Agentic RAG strictly better than Graph RAG?
No, they solve different problems and compose. Agentic RAG decides which source to consult. Graph RAG is one of the sources it can consult, and it is the right one when the question traverses relationships over a small durable set. A well-built agent uses a scoped graph as one of several retrieval tools.
Q: How do you stop an agentic loop from running away?
In code, never in a prompt. A hard iteration cap, a sufficiency threshold (stop at three items graded correct), and a no-new-evidence exit that terminates when two consecutive iterations return only already-seen chunks. Check the budget before each call rather than after, or you overspend by exactly one call every time.
