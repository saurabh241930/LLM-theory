Extended Thinking & Test-Time Compute

Paying for reasoning at inference, and the calls where it is wasted

What "thinking" buys

The model generates intermediate reasoning tokens before its answer, trading latency and output cost for accuracy on problems with a search or verification structure.

Scaling used to mean training a larger model. Test-time compute scales the other axis: spend more tokens at inference on the problem in front of you. The model emits a reasoning block first, and that block can consider approaches, check its own work, and discard dead ends before committing to an answer.

Thinking tokens bill as output tokens, which are the expensive kind. A 4,000-token reasoning block on a mid-tier model costs more than the entire input prompt on most calls. That makes "where does it pay" the only question worth asking.

Which tasks improve, and which do not

Reasoning helps where the task has structure to search: multi-step planning with ordering constraints, arithmetic and unit conversion, debugging from indirect evidence, and anything where a wrong first instinct can be caught by checking.

It does not help on retrieval-bound questions ("what does error 217 mean" is a lookup), classification against a clear rubric, or formatting and extraction. On those the reasoning block restates the rubric and then applies it, which is what it would have done anyway.

Mapping it onto the roles

One role in the running system has a reasoning-shaped job. The high-volume ones do not.
Role Task shape Thinking budget Why
Planner Order steps under DAG constraints, spot missing inputs Generous Runs 1-2 times per run; a wrong order wastes solver-hours
Proposal Weigh graded evidence into one action Moderate Once per diagnosis, and it must justify itself
Tool choice Pick one of four sources None Up to 4x per diagnosis; a four-way choice with a clear rubric
Grader Three-way classification against a rubric None Highest volume in the system; reasoning would dominate cost
Thinking budget follows the same logic as model routing: cost of being wrong, divided by call volume.

The grader is the clearest case. Up to 32 grading calls per diagnosis, each a three-way classification with an explicit rubric. Adding even 500 reasoning tokens per call would multiply the system's dominant cost line for a judgement the rubric already determines.

How it interacts with everything else

Reasoning blocks affect caching, latency budgets, structured outputs and determinism, and each interaction has a practical consequence.
Interacts with Consequence
Prompt caching Caching applies to the input prefix. Thinking is output, so it is never cached and never discounted.
Structured outputs The reasoning block precedes the schema-bound answer. Parse the final content block, never the reasoning.
Latency budgets A 4,000-token reasoning block is seconds of generation. Inside a bounded loop, that multiplies by the iteration count.
Durable replay No change: the call is still a non-deterministic activity. Reasoning does not make it reproducible.
Observability Record reasoning token counts separately, or a cost regression looks like a traffic increase.
Injection defence Unchanged. Reasoning happens inside the model; the closed output enum is still the backstop.
Two of these surprise people: no cache discount, and latency multiplied by loop iterations.
Reasoning budget inside a bounded loop

Symptom: enabling thinking on a loop's per-iteration call pushes diagnosis latency past its deadline, and the activity starts timing out.

Cause: the budget applies per call. Four iterations of a 2,000-token reasoning block is 8,000 generated tokens before any answer is produced.

Mitigation: put the reasoning budget on the single proposal call at the end, not on the per-iteration calls. One considered decision over collected evidence beats four deliberations over partial evidence.

Deciding the budget by measurement

Treat the thinking budget as a parameter you sweep against an eval set, not a setting you pick once.

Returns flatten. Going from no reasoning to a moderate budget often produces most of the available gain on a reasoning-shaped task; doubling again typically produces much less for twice the output bill. Where that knee sits depends on your task, so measure it.

  1. Pick the metric the role actually owns. For the Planner that is plan validity rate on first attempt, not a general benchmark.
  2. Sweep the budget across a few values against a frozen labelled set.
  3. Plot the metric against cost per call and find the knee.
  4. Re-run the sweep when the model version changes, because the knee moves.

This is the same discipline as routing: a number decides it. See Model Routing & Cost Engineering and Evaluating Agent Systems.

Do not treat a reasoning block as an explanation for a user. It is the model's working, not an audit trail, and it can describe a path that differs from how the answer was actually produced. The auditable record is the typed output plus the validated evidence IDs that justify it.

Takeaways

  • Thinking tokens bill as output and are never cached, so the volume calls are exactly where they hurt most.
  • Spend the budget on low-volume, high-stakes reasoning: planning and final proposals.
  • Skip it on rubric-bound classification, retrieval lookups, and extraction.
  • Inside a bounded loop, budget once at the end rather than per iteration.
  • Sweep the budget against an eval metric and find the knee; re-run it when the model changes.
  • A reasoning block is working, not an audit trail.
