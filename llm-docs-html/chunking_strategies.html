Chunking In Depth

Different sources need different chunkers in the same system

The question that matters is not "what size"

A chunk is the unit you are willing to retrieve and show. Its right shape comes from the source's structure, not from a token count you picked once.

Most chunking advice optimises a single global parameter: 512 tokens, 1,000 tokens, 15% overlap. That framing assumes one corpus of one kind of document. Real retrieval systems ingest several sources with genuinely different structure, and a chunker tuned for prose destroys a stack trace.

Two properties decide the chunker for a source. Does the source have exploitable structure? Headings, log line prefixes, and function boundaries are free segmentation signals; flat prose has none. Is a fragment interpretable alone? A paragraph saying "set it to 0.5" is useless without knowing what "it" is and which product is being discussed.

Two of the four lanes do not chunk at all, which is the part generic advice never covers. "Chunk everything" is a habit, not a requirement.

Structure-aware chunking for logs

Take the header, a window anchored on the error, a summary of the repetitive middle, and the tail. Discard the rest.

A solver log is the hardest realistic case and the one nobody teaches. It is 84,000 lines, roughly 95% of it iteration-by-iteration residual tables that are near-identical to each other. Fixed-size chunking over that produces hundreds of interchangeable chunks that all match any query about residuals equally well, which is the same as matching none of them.

Segment What it carries Kept as
Header Version, solver, licence, machine, case setup One chunk, always indexed
Error-anchored window Lines around each error or warning, with context either side One chunk per anchor
Residual history 60,000 numeric lines A computed summary chunk, never raw rows
Tail Final state, exit code, termination reason One chunk, always indexed
Indexing the raw residual table would balloon chunk count for near-zero retrieval signal.

The residual decision is worth sitting with. Those 60,000 lines contain real information, but not information retrieval can use: no query will ever be answered by finding one row of a residual table. A computed summary ("residuals rose over 23 consecutive iterations, diverging from 1e-3") is one chunk that answers the question the rows were evidence for.

Contextualisation: fixing the fragment problem

Prepend 50-100 tokens of situating context to each chunk before embedding, so a fragment means something on its own.

The core weakness of prose chunking is that a chunk gets embedded and retrieved alone, while its meaning depended on the document around it. "Set pseudo-time-step to 0.5" means nothing without knowing the product, the release, and which failure mode the section addresses.

Contextualisation runs at ingest: a small model reads the chunk plus its surrounding document and writes a short preamble naming what the chunk is about. That preamble is embedded with the chunk.

# Before
"Set pseudo-time-step to 0.5 and re-run. If residuals continue rising,
 reduce the Courant number by half."

# After contextualisation, embedded together
"[Fluent 2026 R2 · Troubleshooting · AMG solver divergence]
 Set pseudo-time-step to 0.5 and re-run. If residuals continue rising,
 reduce the Courant number by half."

Doing this once at ingest rather than per query is the single largest cost lever in the ingestion pipeline. The chunk is written once and read thousands of times, so the per-chunk model call amortises to nothing. Computing it at query time would be the same work repeated on every request.

Contextualisation also improves keyword search, not only vector search, because the preamble adds the product and version tokens that the fragment was missing. Both branches of a hybrid query benefit from the same preprocessing.

Scrubbing, deduplication and metadata

Every chunk is scrubbed before embedding, deduplicated within its own source, and stamped with the fields every later query filters on.

Scrubbing strips paths, hostnames, usernames, and licence-server names. A path keeps its basename and loses its directory: bracket_v3.cas is useful retrieval signal, /home/jsmith/projects/acme-confidential/ is a liability. Scrubbing happens before embedding, so the vector never encodes the removed detail either.

Deduplication runs within a source, never across sources. A skill quoting a documentation paragraph is not a duplicate of that paragraph; it carries the team's judgement that this specific passage matters for this specific failure. Cross-source dedupe would silently delete exactly the signal that makes skills worth indexing.

Metadata field Used for
tenant_id The isolation boundary; a SQL predicate on every query
solver, solver_version Pre-filter and grader rule; prevents right-answer-wrong-version
embedding_model Makes an embedding migration a dual-write rather than a rewrite
valid_to Retires superseded chunks without deleting history
run_id, step_name Scopes log chunks tightly enough to skip the reranker
Metadata is what lets the funnel's first stage be free and correct.

What not to index

Unversioned plausible content is worse than no content, because the grader cannot tell stale from current without a version field.

Chunk-size drift after a docs redesign

Symptom: retrieval quality drops after a documentation site redesign, with no change to the retrieval code.

Cause: heading-boundary chunking depends on the HTML structure. A redesign that changes heading levels produces chunks of a different shape.

Mitigation: assert distribution properties at ingest (median chunk size, share of chunks under a floor) and fail the ingest run when they move sharply, rather than discovering it through degraded answers weeks later.

Takeaways

  • Pick the chunker per source. Structure-aware for logs, heading-bounded prose for docs, whole-file for playbooks, none for already-structured records.
  • Two of four lanes do not chunk at all. "Chunk everything" is a habit, not a requirement.
  • Contextualise at ingest, not at query time. Write once, read thousands of times.
  • Scrub before embedding, and deduplicate within a source rather than across sources.
  • Stamp tenant, version, embedding model and validity on every chunk; that metadata is what makes the funnel's first stage free and correct.
  • Unversioned plausible content is worse than none.
