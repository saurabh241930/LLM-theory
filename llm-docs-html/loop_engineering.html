Loop Engineering

Iteration caps, stop conditions, and budgets that live in code

What an agent loop actually is

The model reads state and a tool list, picks one tool and arguments, something outside the model runs it and feeds the result back as new state. Repeat until the model says done.

There is no hidden reasoning engine and no separate planning module inside the model. Every "plan", "decide", or "diagnose" step in any agent framework is this same loop wearing a different prompt and a narrower tool list.

The loop has one structural weakness worth naming early: the model's own output decides what happens next. If nothing stands between the model's text and a real side effect, then starting a cluster job or writing a field is one unsupervised step away from a hallucinated argument. Everything interesting in agent design is about how much you let the raw loop touch, and how much you wrap in validation, typed contracts, and places to stop and ask a human.

Why "let the model decide when to stop" fails

A model asked to stop when it has enough information will sometimes decide that on iteration two and sometimes on iteration forty. The variance is not a prompt problem. The model has no reliable sense of how much it has already spent, and no view of what the next call costs.

Loop control belongs in the calling code, where the iteration count and the running spend are ordinary variables. The model contributes evidence; the code decides whether that is enough.

A loop contract, written out

Four iterations, two LLM calls per iteration, one final call: a hard ceiling of nine calls, enforced in Python.

The SAF Diagnoser's loop is a useful shape because every number in it is defensible. Per iteration it makes one tool-choice call and one batched grading call. After the loop it makes one proposal call. Four iterations gives a ceiling of nine LLM calls, and the loop exits on whichever of three conditions fires first.

Three exits; every one of them produces a typed action, including "found nothing".
MAX_ITERS = 4
MIN_CORRECT = 3

async def diagnose_agentic(failure, tools, grade, propose) -> RemediationAction:
    query = build_signature(failure)
    kept: list[GradedEvidence] = []
    seen: set[str] = set()

    for _ in range(MAX_ITERS):
        tool_name, query, k = await choose_tool(failure, query, kept)
        cands = [e for e in await tools[tool_name](query, k) if e.ref not in seen]
        if not cands:
            break                                   # stop: no new evidence
        seen.update(e.ref for e in cands)
        graded = await grade(failure, cands)        # one batched call
        kept += [g for g in graded if g.grade != "incorrect"]
        if sum(1 for g in kept if g.grade == "correct") >= MIN_CORRECT:
            break                                   # stop: sufficiency

    if not kept:
        return RemediationAction(kind=RemediationKind.ESCALATE,
                                 reason="no evidence graded relevant after retrieval",
                                 evidence=[], confidence=0.0, requires_approval=True)
    return await propose(failure, kept)

Notice what the empty case does. Finding nothing returns a typed escalation, not an exception and not a guess. A loop that cannot express "I found nothing" will invent something instead.

Budgets that survive a crash

A counter in a local variable is lost on restart. Budget belongs in durable state, checked before the call that would exceed it.
class Budget(BaseModel):
    max_usd: float = 25.0
    max_wall_clock_s: int = 6 * 3600
    max_llm_calls: int = 60
    max_solver_hours: float = 4.0

def check_budget(budget, spent_usd, llm_calls, solver_hours, *, kind: str) -> None:
    if spent_usd >= budget.max_usd:
        raise BudgetExceeded(f"cost {spent_usd:.2f} >= cap {budget.max_usd:.2f}")
    if kind == "llm" and llm_calls >= budget.max_llm_calls:
        raise BudgetExceeded(f"llm call cap {budget.max_llm_calls} reached")
    if kind == "solver" and solver_hours >= budget.max_solver_hours:
        raise BudgetExceeded(f"solver-hour cap {budget.max_solver_hours} reached")

Two details matter more than the code. First, the check runs before the call rather than after, so the call that would breach the cap never fires. Checking afterwards means you always overspend by exactly one call, which is fine at $0.001 and painful at a solver-hour.

Second, the budget lives on durable workflow state rather than in a side table. Because the orchestrator's state replays deterministically, the number cannot be double-counted by a retry or lost to a crash, and it can be read live by a status query without a separate accounting system.

Runaway loops

Symptom: a run burns its entire call budget without making progress.

Cause: a replan or diagnosis loop keeps calling the same tool with a near-identical query, undetected.

Mitigation: check the budget before every call, and track a seen set of evidence IDs so a rewrite that keeps re-finding the same chunks terminates the loop instead of paying for it four times.

Retry storms

Symptom: one schema-invalid output burns dozens of retries across every concurrent run at once.

Cause: the retry policy defaults to unlimited attempts, and a validation failure looks like any other exception unless it is told otherwise.

Mitigation: set an explicit maximum attempts on every LLM activity, and mark validation failures non-retryable so a bad plan goes to a replan with feedback instead of retrying the identical prompt.

Latency: iterations multiply, so batch inside them

Four iterations of sequential per-candidate grading is the difference between a 7-second diagnosis and a 40-second one.

The loop above grades a whole batch of candidates in one call rather than one call per candidate. With eight candidates and four iterations, per-candidate grading is 32 sequential round trips. The same work batched is four.

Retrieval latency in the loop

Symptom: a diagnosis takes 40 seconds and starts closing in on the activity heartbeat timeout.

Cause: four iterations of retrieval and grading, each run sequentially per candidate.

Mitigation: gather the grading calls concurrently, hold the iteration cap and k as constants, and give the activity a hard deadline that returns an escalation on timeout rather than hanging.

Where the loop cap belongs in the prompt: nowhere

"Use at most four iterations" in a system prompt is a request. A for loop is a guarantee.

This is the recurring lesson across every control in an agent. Anything expressed as an instruction to the model is advice it usually follows. Anything expressed in the calling code holds whether or not the model behaves as expected, including when retrieved text is actively trying to change its behaviour.

The same principle drives allow-lists over "please only call these tools", SQL tenant predicates over "only consider tenant A's data", and closed enums over "return one of these six actions". See Structured Outputs & Guardrails.

Takeaways

  • Loop control belongs in code. The model contributes evidence; the calling code decides whether it is enough.
  • Name every exit. Sufficiency, no-new-evidence, and a hard iteration cap, each producing a typed result.
  • A loop that cannot say "I found nothing" will invent something. Make the empty case a first-class return value.
  • Check the budget before the call, not after, and keep it in durable state so a crash cannot lose it.
  • Batch inside iterations. 32 sequential round trips becomes 4 for the same tokens.
