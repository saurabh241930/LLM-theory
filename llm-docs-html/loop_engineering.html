Loop Engineering

Caps, stop conditions and budgets, all in code

What an agent loop is

Read state, pick a tool, run it outside the model, feed the result back. Repeat.
flowchart LR S["State + tool list"] --> M["Model picks one tool
and arguments"] M --> X["Your code runs it"] X --> R["Result becomes new state"] R --> S M -.->|"model says done"| E["Exit"]

There is no hidden planning module. Every "plan", "decide" or "diagnose" step in any framework is this loop wearing a different prompt and a narrower tool list.

It has one structural weakness. The model's own output decides what happens next. If nothing stands between that output and a real side effect, a hallucinated argument is one step from starting a cluster job.

Why "let the model decide when to stop" fails

Asked to stop when it has enough, a model stops at iteration two sometimes and iteration forty other times. That variance is not a prompt problem.

The model has no reliable sense of what it has already spent, and no view of what the next call costs. Loop control belongs in the calling code, where iteration count and running spend are ordinary variables.

A loop contract

Four iterations, two calls each, one final proposal. A ceiling of nine, enforced in Python.
flowchart TD F["Failure record"] --> C["Choose tool and query"] C --> R["Retrieve top-k"] R --> G["Grade the batch
one call, not one per candidate"] G --> D{"Stop?"} D -->|"3+ graded correct"| P["Propose"] D -->|"no new evidence"| P D -->|"iteration 4"| P D -->|"budget remains"| C P --> W["Return typed action"]
Exit Prevents
3+ graded correct Paying for evidence you no longer need
Two iterations return nothing new Rewriting a query that keeps finding the same chunks
Iteration 4, or budget spent Unbounded spend on a hard failure 
MAX_ITERS = 4
MIN_CORRECT = 3

for _ in range(MAX_ITERS):
    tool_name, query, k = await choose_tool(failure, query, kept)
    cands = [e for e in await tools[tool_name](query, k) if e.ref not in seen]
    if not cands:
        break                                   # stop: no new evidence
    seen.update(e.ref for e in cands)
    graded = await grade(failure, cands)        # one batched call
    kept += [g for g in graded if g.grade != "incorrect"]
    if sum(1 for g in kept if g.grade == "correct") >= MIN_CORRECT:
        break                                   # stop: sufficiency

if not kept:
    return RemediationAction(kind=RemediationKind.ESCALATE,
                             reason="no evidence graded relevant",
                             evidence=[], confidence=0.0, requires_approval=True)
return await propose(failure, kept)

Note the empty case. Finding nothing returns a typed escalation, not an exception and not a guess. A loop that cannot say "I found nothing" will invent something.

Budgets that survive a crash

Check before the call, not after. Keep the counter in durable state.
flowchart LR subgraph A["Check after"] A1["Make call"] --> A2["Add cost"] --> A3{"Over?"} A3 -->|yes| A4["Too late.
Always over by one."] end subgraph B["Check before"] B1{"Would this
exceed?"} -->|yes| B2["Never fires"] B1 -->|no| B3["Make call"] end 
class Budget(BaseModel):
    max_usd: float = 25.0
    max_wall_clock_s: int = 6 * 3600
    max_llm_calls: int = 60
    max_solver_hours: float = 4.0

Four dimensions, because money is not the only thing that runs out. Being over by one call is fine at $0.001 and painful at a solver-hour.

The budget lives on durable workflow state, so a retry cannot double-count it and a crash cannot lose it.

Runaway loops

Symptom: a run burns its whole call budget without progress.

Cause: the loop keeps calling the same tool with a near-identical query.

Mitigation: check the budget before every call, and track a seen set of evidence IDs so a rewrite that re-finds the same chunks terminates.

Retry storms

Symptom: one invalid output burns dozens of retries across every concurrent run.

Cause: unlimited retry policy, and a validation failure looks like any other exception.

Mitigation: explicit max attempts on every model call. Mark validation failures non-retryable so a bad plan replans with feedback instead of repeating the prompt.

Batch inside iterations

Iterations multiply round trips. Same tokens, very different wall clock.

~40 s"] end subgraph B["Batched per iteration"] B1["1 call × 4 iterations"] --> B2["4 round trips
~7.5 s"] end
Retrieval latency in the loop

Symptom: diagnosis takes 40 seconds and closes in on the activity heartbeat.

Cause: four iterations of retrieval and grading, run sequentially per candidate.

Mitigation: gather grading calls concurrently, hold the cap and k as constants, and give the activity a hard deadline that returns an escalation on timeout.

The cap does not belong in the prompt

"Use at most four iterations" is a request. A for loop is a guarantee.
flowchart LR subgraph P["In the prompt"] P1["'only call these tools'"] --> P2["usually obeyed"] end subgraph C["In the code"] C1["allow-list, for-loop,
SQL predicate, enum"] --> C2["always holds"] end

The same principle drives allow-lists over "please only call these", tenant predicates over "only consider tenant A", and closed enums over "return one of these six". See Structured Outputs.

Takeaways

  • The model contributes evidence. The calling code decides whether it is enough.
  • Name every exit: sufficiency, no new evidence, and a hard cap.
  • Make "found nothing" a real return value, or the model fills the gap.
  • Check budgets before the call, in durable state, across four dimensions.
  • Batch inside iterations. 32 round trips becomes 4 for the same tokens.
