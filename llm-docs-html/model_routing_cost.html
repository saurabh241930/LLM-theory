Model Routing & Cost Engineering

Routing by job, prefix caching that actually hits, and budgets that survive a crash

One model for every call is the expensive default

Route by what the call needs. Planning wants the strongest reasoning over the largest context; grading is a narrow, high-volume judgement that does not.

An agent makes several structurally different kinds of call, and they have different requirements. Planning happens once or twice per run and decides how a solver-hour gets spent, so being wrong is expensive. Grading happens up to 32 times per diagnosis and answers a three-way classification with a clear rubric.

Role Model Calls per diagnosis Tokens in / out Cost
Planner Opus 5 1-2 per run ~6,000 / ~1,500 ~$0.068 per run
Tool choice Haiku 4.5 ≤ 4 ~800 / ~50 ~$0.004
Grade (batched) Haiku 4.5 ≤ 4 ~1,850 / ~60 per candidate ~$0.068 worst case
Proposal Sonnet 5 ≤ 1 ~9,800 / ~700 ~$0.027
Ceiling — 9 — ~$0.11 worst, ~$0.046 typical
The expensive model runs once; the cheap model absorbs the volume.

The trade is real and worth stating plainly: routing across three models means three cost curves to watch instead of one, and a quality regression on the cheap model shows up as a rising escalation rate rather than an error. That is cheap to catch with a frozen labelled set and cheap to fix by re-routing.

How to decide which call gets which model

Ask what a wrong answer costs, then how many times per run the call happens.
Signal Points to the strong model Points to the cheap model
Cost of being wrong A wasted solver-hour, a bad approval One noisy candidate among eight
Call volume Once or twice per run Tens per run
Task shape Open-ended reasoning, long context, ordering Classification against an explicit rubric
Recoverability Hard to undo A later stage catches it
Grading is high-volume, rubric-bound, and individually recoverable, which is the cheap-model profile exactly.

One rule keeps this honest: route by measurement, not by instinct. Move a role to a cheaper model, run the frozen labelled set, and look at precision per class. If it holds, keep the saving. The decision is a number, not a preference.

Prefix caching: the mechanics people get wrong

Prefix caching keys on an exact byte-for-byte prefix, and short prompts on small models do not qualify at all.

Prompt caching stores the processed prefix of a request so a later request sharing that exact prefix skips re-processing it. Two constraints decide whether you ever benefit.

The prefix must match exactly. One retrieved chunk placed above your stable instructions invalidates everything after it. This is why ordering by volatility matters: stable instructions, tool schemas and resources first, retrieved evidence last. See Context Engineering.

There is a minimum cacheable length. Small models typically require a larger minimum prefix than their prompts usually reach. The grader's prompt is a few hundred tokens against a minimum in the low thousands, so prompt caching does nothing for the highest-volume call in the system.

Call Prompt size Prefix caching helps? What to do instead
Planner ~6,000 tokens, stable schema block Yes Order the schema block ahead of the intent
Proposal ~9,800 tokens, stable system prefix Yes, after ~2 reads in the window Keep evidence last
Grader A few hundred tokens No, below the minimum Cache verdicts by (query hash, evidence ID, model)
Caching the wrong layer is a common source of "we added caching and nothing changed".

Caching verdicts instead of prompts is the move worth remembering. The grader answers a pure function of (query, evidence, model), so the result is cacheable even when the prompt is not.

The largest lever is earlier than any of this: precomputing contextualised chunks at ingest rather than per query. The chunk is written once and read thousands of times. See Chunking In Depth.

Budgets as durable state

A typed budget object decremented before every priced call, living in crash-proof state rather than a side table.
class Budget(BaseModel):
    max_usd: float = 25.0
    max_wall_clock_s: int = 6 * 3600
    max_llm_calls: int = 60
    max_solver_hours: float = 4.0

PRICES = {  # USD per million tokens, input/output
    "claude-opus-5":   (5.00, 25.00),
    "claude-sonnet-5": (2.00, 10.00),
    "claude-haiku-4-5": (1.00,  5.00),
}

def charge_llm(model: str, input_tokens: int, output_tokens: int) -> float:
    cin, cout = PRICES[model]
    return (input_tokens * cin + output_tokens * cout) / 1e6

Four dimensions, because money is not the only thing that runs out. A run can be cheap in dollars and still burn six hours of wall clock or four solver-hours.

Two properties make this work. The check runs before the call that would exceed the cap, so you never overspend by one call, which is the difference between $0.001 and a solver-hour. And the budget lives on durable workflow state, so a retry cannot double-count it and a crash cannot lose it. See Agentic Workflows.

Cost tracked in a side table

Symptom: the recorded spend for a run disagrees with the provider invoice, and nobody can say which is right.

Cause: an activity writes its cost to a separate table after the call. A retry writes twice; a crash between the call and the write loses one.

Mitigation: return the cost as part of the activity's typed result so it replays deterministically with the run's own history, and expose it through a live query rather than a separate counter.

What to cut first when cost becomes binding

In order: the reranker where the pool is already narrow, then more routing to the mid model, then the loop cap.
  1. The reranker, selectively. Where the pre-filtered pool is within ~3x the final top-k, reranking buys almost no new ordering. Dropping it there is nearly free and does not touch accuracy.
  2. Route more diagnoses to the mid model. Reserve the strongest model for low-confidence escalations rather than every proposal.
  3. Lower the loop iteration cap. Going from 4 to 3 is a visible trade against escalation rate, which is the honest kind of cut: it shows up in a metric rather than silently.

The ordering matters because the first two are invisible to quality and the third is not. A cut that shows up in a number somebody watches is a decision; a cut that shows up nowhere is a slow regression.

Takeaways

  • Route by cost-of-being-wrong and call volume. High-volume rubric-bound classification is the cheap model's job.
  • Prefix caching needs an exact prefix and a minimum length. Order by volatility, and cache verdicts when prompts are too short to qualify.
  • Precompute at ingest before optimising anything at query time.
  • Check budgets before the call, across dollars, wall clock, calls, and solver-hours.
  • Return cost as part of the typed activity result so it cannot be double-counted or lost.
