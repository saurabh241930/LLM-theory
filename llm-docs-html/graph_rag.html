Graph RAG

When a graph beats an index, and when it is an expensive mistake

What Graph RAG replaces

A flat chunk index answers "what text looks like this question". A graph answers "what is connected to this thing, and how".

Standard RAG embeds chunks and retrieves the nearest ones. That works when the answer sits in a passage that resembles the question. It fails on questions whose answer is a relationship spanning several documents, because no single chunk contains the connection.

Graph RAG builds an entity graph instead: nodes for entities, typed edges for relationships, and often LLM-generated community summaries over clusters. A query traverses relationships rather than ranking by similarity.

The two questions that decide it

Do the questions traverse relationships? "Which failures were fixed by lowering the Courant number, and did those runs stay green?" is a two-hop walk. "What does error 217 mean?" is a lookup, and a graph adds nothing to it.

How fast does the index go stale? Graph construction is the expensive part. If the corpus reissues on a release cadence, you pay that cost again every release.

The cost nobody budgets for

Full Graph RAG's index is LLM-built, which makes rebuilds expensive enough to change the decision.

Constructing an entity graph over a large corpus means running a model over every document to extract entities and relationships, then summarising communities. Published figures for indexing roughly a million tokens land in the region of a few hours of processing and a real bill. Over a documentation corpus that reissues per product release, that is a recurring cost against a corpus whose questions are mostly lookups.

Same technique, two scopes, opposite answers.

Graph RAG is not wrong here; it is aimed at the wrong corpus. The documentation corpus is large, fast-changing, and mostly asked lookup questions. The failure-to-remediation-to-outcome data is small, structured, durable, and asked exactly the relationship question a graph is good at.

The scoped graph, concretely

Two Postgres tables and a recursive CTE capped at two hops. No graph database, no LLM call.
erDiagram MEM_NODES { string node_id string node_type string tenant_id vector embedding } MEM_EDGES { string edge_id string src_node_id string dst_node_id string relation float weight } MEM_NODES ||--o{ MEM_EDGES : connects

Nodes are failure signatures, remediation kinds, and skill tags. Edges are typed and weighted: fixed_by, similar_to, cites. Every row carries a tenant.

WITH RECURSIVE hop(node_id, relation, depth, path) AS (
    SELECT n.node_id, NULL::text, 0, ARRAY[n.node_id]
    FROM   mem_nodes n
    WHERE  n.node_id = $1                    -- nearest failure-signature node
  UNION ALL
    SELECT e.dst_node_id, e.relation, h.depth + 1, h.path || e.dst_node_id
    FROM   hop h
    JOIN   mem_edges e ON e.src_node_id = h.node_id
    WHERE  h.depth < 2                       -- cap at two hops
      AND  NOT e.dst_node_id = ANY(h.path)   -- no cycles
)
SELECT n.node_id, n.node_type, h.relation, h.depth
FROM   hop h
JOIN   mem_nodes n ON n.node_id = h.node_id
WHERE  h.depth > 0
  AND  n.tenant_id = $2
ORDER  BY h.depth, h.node_id;

Entry into the graph is a vector search for the nearest failure signature; traversal from there is relational. That hybrid is the practical shape: embeddings find the door, edges walk the building.

The depth cap and the cycle guard both matter. Without the cap, a well-connected node returns most of the graph. Without the path check, a cycle runs forever.

When to reach for a real graph database

A recursive CTE handles two hops over a small graph. Deeper traversals over millions of edges are what graph engines are for.
Signal Stay in Postgres Move to a graph engine
Traversal depth 1-2 hops Variable or unbounded
Graph size Thousands of edges Tens of millions
Query shape Fixed, known in advance Pattern matching, shortest path
Operational cost Already running Postgres A new system to run and secure
The graph living in the same database as the retrieval store means one place tenant filters can be forgotten, not two.

Keeping the graph in the same Postgres instance as the vector store is a real operational simplification. One backup story, one connection pool, one place to enforce tenant isolation. A separate graph database buys traversal power and costs a second system where a filter can be missed.

Failure modes

Graphs fail quietly, because a wrong edge looks exactly like a right one.
Edges recording coincidences

Symptom: the graph confidently recommends a fix that never actually worked.

Cause: a fixed_by edge was written because a retry passed, when something unrelated is what changed.

Mitigation: write an edge only when the retry reached terminal success and the remediation was the sole change. Decay edge weight when a reused fix stops working. See Agent Memory Systems.

Embedding model change breaks graph entry

Symptom: similar-failure recall stops surfacing precedent after an embedding upgrade, with no error anywhere.

Cause: entry into the graph is a vector search, and vectors from two models are not comparable.

Mitigation: stamp embedding_model on every node, dual-write during cutover, drop the old column once every reader has moved.

Tenant leakage through a traversal

Symptom: one tenant's engineer sees a remediation derived from another tenant's run.

Cause: the tenant filter was applied to the entry lookup but not to the traversal, so hop two crossed the boundary.

Mitigation: filter on tenant at every level of the recursion, not only at entry, and assert zero cross-hits on a two-tenant fixture in CI.

Takeaways

  • Two questions decide it: do queries traverse relationships, and how fast does the index go stale.
  • Full Graph RAG's index is LLM-built, so a corpus that reissues per release pays that bill repeatedly.
  • A small graph written as a side effect of work already happening is incremental and costs nothing to maintain.
  • Embeddings find the entry node; edges do the traversal. Cap the depth and guard against cycles.
  • Filter on tenant at every level of the recursion, not only at entry.
