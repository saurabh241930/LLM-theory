Designing an Agent for Long-Running Simulation Jobs

The running case study: a durable orchestrator over Ansys SAF

The problem in one paragraph

An engineer types "bracket fatigue at 200 Hz" and wants a finished simulation report. The solve takes four hours, costs cluster-time, and can fail six different ways.

Ansys SAF (Solution Application Framework) turns a simulation workflow into a web application. It ships an HTTP API, a state engine that tracks every field, and an MCP server handing that API to an LLM as callable tools. What it does not ship is a brain. Nothing plans a run from a sentence, waits out a four-hour solve without holding a thread, reads a solver log and proposes a fix, or asks a human before something expensive.

That gap is the design problem. It is a good teaching example because every hard part of agent engineering shows up for a concrete reason rather than as a topic on a syllabus. The run outlives the request, so you need durable execution. The solver burns cluster-hours, so you need budgets and approval gates. The logs are redacted, so you need retrieval. The model can hallucinate a step name, so you need validation against a real dependency graph.

Every other page in this section maps its concept back to this system.

Why not a thin ReAct loop?

Three architectures were scored against what a solver run actually needs. Two lost on durability.
Criterion A: Thin ReAct loop B: Durable orchestrator C: Multi-agent swarm
Durability across crashes None, in-memory conversation Full, state survives process death Partial, depends on each agent
Human-in-the-loop Awkward, nothing to pause Native, can wait indefinitely Ambiguous, unclear who owns the pause
Determinism / auditability Low, one opaque transcript High, typed logged steps Low, agent chatter is hard to replay
Cost predictability Poor, unbounded conversation Good, budget checked every step Poor, inter-agent chatter multiplies calls
Fit to a DAG workflow Weak, no structural check Strong, plan validated against the DAG Weak, no single place enforces order
Three architectures against the requirements a solver run actually has.

B wins on a checklist, not on taste. A solver run takes hours, so only B survives without holding a thread the whole time. A run needs a human sign-off that might not arrive for a day, so only B can pause indefinitely. A step can report Completed while its outputs are OUTOFDATE, and that is the kind of fact you want checked by typed code between LLM calls rather than by a model reading its own conversation history.

Approach A is honest and simple, and it fails the moment a job outlives one request. Approach C adds coordination overhead without buying back durability, and it makes the audit trail worse: "why did the agent set this field to 0.85?" gets much harder to reconstruct.

Read it left to right and one fact falls out: nothing in the LLM box talks to SAF, and nothing in the SAF box knows an LLM exists. The workflow sits between them and decides when each side runs. That separation is the entire argument for the architecture, drawn as a picture.

The main loop

Plan, maybe wait for approval, execute a step, maybe wait for a solver, and on failure diagnose before deciding what happens next.
stateDiagram-v2 [*] --> PLANNING PLANNING --> AWAITING_PLAN_APPROVAL: plan needs approval PLANNING --> RUNNING: plan auto-approved AWAITING_PLAN_APPROVAL --> RUNNING: approve AWAITING_PLAN_APPROVAL --> ABORTED: reject RUNNING --> WAITING_SOLVER: long-running transaction WAITING_SOLVER --> RUNNING: terminal, next step WAITING_SOLVER --> DIAGNOSING: MethodState failed RUNNING --> DIAGNOSING: activity error DIAGNOSING --> RUNNING: retry / adjust_field / rerun_upstream DIAGNOSING --> AWAITING_APPROVAL: escalate AWAITING_APPROVAL --> RUNNING: approve AWAITING_APPROVAL --> FAILED: reject or SLA timeout RUNNING --> COMPLETED: all steps done RUNNING --> FAILED: budget exhausted

The loop has one entry point for new work, "execute the next step," and approval, polling and diagnosis all route back through it. That single funnel is what keeps the state machine small enough to draw. Nothing in the diagram is decided by an LLM reading prose: the workflow branches only on a validated Plan, a MethodState enum, or a typed RemediationAction.

What it costs, and what it promises

A design without numbers reads as unbuilt. These are the ones to memorise.
Requirement Target How it is measured
Durability A worker crash mid-run loses zero plan state and never resubmits a completed solve Chaos test: kill a worker mid-poll; idempotency key blocks the duplicate
Diagnosis latency Under 60 s from failure to proposed action p95 of the diagnose span in the eval harness
Cost per run Median LLM spend under $5 against a $25 ceiling Cost summed across every step result and diagnoser call
Tenant isolation Zero cross-tenant rows returned by any retrieval query, ever Fuzz test queries the store as tenant A asking about tenant B
Solver-hours budget A run halts before exceeding 4.0 solver-hours Workflow decrements per step and refuses to start one that would exceed it
Non-functional requirements, each with a concrete target and a test.

Per-diagnosis LLM budget; the 9-call ceiling is enforced in code, not asked for in a prompt.

Three models rather than one is a deliberate trade. Planning needs the most capable reasoning over the largest context. Grading is a narrow, high-volume judgement call that does not. Routing this way costs three cost curves to watch instead of one, and buys roughly an order of magnitude on the calls that dominate volume. See Model Routing & Cost Engineering.

The failure modes worth knowing

Each of these is a real bug with a symptom you can recognise in a log.
The 600-second wait ceiling

Symptom: the wait tool returns a timeout while the solver is still iterating.

Cause: the tool blocks inside one HTTP request and the framework caps it at 600 s, against solver jobs that default to a one-week maximum.

Mitigation: never wait inside a tool call. Poll status from a durable timer loop every 30 s with jittered backoff, outside the request that started the transaction.

Completed and out-of-date coexist

Symptom: an agent reports a finished run on numbers that no longer match its inputs.

Cause: writing a field marks every downstream field stale without touching method status, so a step reads Completed forever while its outputs go stale underneath it.

Mitigation: the done predicate checks both axes: status is Completed and every expected output is UPTODATE.

Hallucinated step names

Symptom: the first activity fails with unknown step 'meshing' on a solution whose step is named mesh.

Cause: structured outputs constrain shape, not membership. A string field compiles to a JSON Schema string, and nothing stops a plausible-sounding invention.

Mitigation: validate every step and transaction against the real schema before anything runs, and feed the valid names back as correction so the model fixes itself in one replan rather than looping.

Prompt injection through a solver log

Symptom: a diagnosis recommends downloading every project file.

Cause: a log line or shared runbook reads as an instruction, and the model treats it as one.

Mitigation: retrieved text goes into the prompt inside delimited, labelled blocks under an explicit policy that embedded instructions are data to report, never commands to follow. The backstop is a closed enum: injected text cannot name an action that does not exist. See Prompt Injection Defence.

Poisoned write-back memory

Symptom: a fix marked successful because a retry happened to pass for an unrelated reason, then recommended confidently later.

Cause: the run wrote back a coincidence as a lesson.

Mitigation: write back only when the retry reached terminal success and the remediation was the sole change. Decay edge weight when a reused fix stops working. Require human approval before a novel fix kind enters memory.

Takeaways

  • The architecture question is a checklist against real constraints, not a preference. A four-hour solve and a day-long approval eliminate two of three candidate designs on their own.
  • Keep the orchestrator deterministic. Every LLM call and every HTTP call is a retryable activity, because both are exactly the kind of I/O a replay cannot trust.
  • The model proposes and the guardrails dispose. Allow-lists, budgets, approval gates and evidence-ID validation are all deterministic code the model cannot argue with.
  • Have numbers ready: a 600-second wait ceiling, a 9-call diagnosis budget, ~$0.046 per diagnosis, a 4.0 solver-hour cap. A design without numbers reads as unbuilt.
  • State the trade-off you accepted, not only the property you gained.
