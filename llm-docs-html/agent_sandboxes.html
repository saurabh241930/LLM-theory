Agent Sandboxes & Code Execution

Isolation boundaries, credential scope, and what an escaped process can reach

Why agents end up executing code at all

Some questions are cheaper to compute than to reason about, and a model that must answer them from text will guess.

Three situations push an agent toward running code. The first is arithmetic over data: classifying 60,000 residual values from a solver log is a five-line script and an impossible reading task. The second is format handling: parsing a proprietary binary result file needs a library, not a language model. The third is verification: running the test suite is the only honest way to know whether a proposed fix works.

Each of those is a genuine reason. What they share is that the code's output becomes model context, so the execution boundary is also a trust boundary in both directions: untrusted data goes in, and whatever comes out shapes the next decision.

In the running example

The fluent-divergence skill bundles scripts/classify_residuals.py, which reads the last 2,000 lines of a solver log and returns one of four classes. The model never reads 84,000 lines of residuals. It reads a label. See Agent Skills.

Isolation levels, and what each one actually buys

Pick the weakest boundary that contains the worst thing the code could do, and be honest about what the weak ones do not stop.
Level Boundary Stops Does not stop Startup
Restricted interpreter Language-level, same process Casual mistakes A determined escape; shares your memory space ~0 ms
Subprocess + rlimits OS process, dropped privileges Runaway CPU and memory, crashes Filesystem and network reach ~10 ms
Container Namespaces, cgroups, seccomp Filesystem, network, resource abuse Kernel-level escapes ~100 ms-1 s
MicroVM Hardware virtualisation Kernel escapes Side channels on shared hardware ~125 ms
Cost rises with isolation; so does what survives a compromise.

A restricted interpreter running in your own process is the option that most often gets chosen and most often should not. It shares your memory space, your file descriptors, and your credentials. It is reasonable for arithmetic on data you produced and unreasonable for anything touching content a third party could shape.

For a system where scripts are hand-written, version-controlled, and reviewed, a subprocess with dropped privileges and hard resource limits is usually the right level. Model-authored code needs a container at minimum.

The boundary that matters most is the credential

Process isolation limits what code can run. Credential scope limits what a compromise can reach, which is the part that ends up in the incident report.

An agent typically holds a token that authenticates the user who started the run. If sandboxed code can read that token, isolation has bought very little: the escape does not need to break out of the container when it can make authenticated API calls from inside it.

Rule Why
No ambient credentials in the sandbox environment Environment variables and mounted credential files are the first thing hostile code reads
Data in by argument or stdin, results out by stdout A narrow interface is auditable; a shared filesystem is not
Network denied by default Most analysis scripts need none, and exfiltration needs one open egress
Short-lived, narrowly scoped tokens when a call is genuinely needed A token measured in minutes limits the window; the user's own token lasts the run
Wall-clock and memory caps enforced by the OS A timeout in application code does not stop a busy loop reliably
Least privilege applied to the process, not only to the user.
A token that outlives its purpose

Symptom: a step running fine for three hours suddenly fails every API call with 401, or worse, a long-lived token turns up somewhere it should not be.

Cause: the access token handed to the activity when the step started has an expiry measured in minutes, while the run is measured in hours. Holding one token for the life of a four-hour run is both fragile and a large blast radius.

Mitigation: re-issue a fresh, narrowly scoped credential per activity at the point it actually calls out, rather than once at workflow start. An expiry mid-poll then costs one retried activity, not a failed run.

Output is untrusted input

Whatever the sandbox prints goes into the model's context, so a script reading a hostile log can become an injection vector.

This is the direction people forget. The sandbox protects your infrastructure from the code. It does nothing to protect the model from the code's output. A script that echoes lines from a solver log is a pipe from untrusted text straight into the prompt.

Three habits close it. Return structured values rather than free text, so a classifier returns one of four enum labels instead of a paragraph. Cap output length, because a script that returns 100,000 lines has already cost you the context window. Wrap whatever does come back in the same delimited, labelled block any other untrusted source gets, under the same policy that instructions inside it are data to report rather than commands to follow.

In the running example

classify_residuals.py returns one of amg_divergence, fp_exception, viscosity_limited, cfl_too_high. A hostile log can make it return the wrong label. It cannot make it return an instruction, because those four strings are the entire output vocabulary. See Prompt Injection Defence.

Reproducibility: a sandbox is also a versioned artefact

An agent run you cannot re-execute is an agent run you cannot debug.

Sandboxes drift the way any environment drifts. A script that worked in March fails in September because a dependency moved. When the script is part of a diagnosis path, that drift shows up as degraded agent quality with no code change to blame.

  • Pin the image by digest, not by a floating tag.
  • Version bundled scripts with the skill that carries them, and record which product versions they were verified against.
  • Record the image digest on the run's trace, so "why did this run behave differently" is a lookup.
  • Run the skill's fixed (input, expected output) pairs in CI whenever the image or the script changes.
Cold-start latency inside a bounded loop

Symptom: diagnosis latency jumps by seconds whenever a script runs, and the loop starts closing in on its deadline.

Cause: a fresh container per invocation inside a loop that may run four iterations.

Mitigation: keep a warm pool for the common scripts, or run trusted version-controlled scripts as a subprocess and reserve containers for model-authored code. Give the execution a hard deadline that returns a typed failure rather than hanging the iteration.

Takeaways

  • Choose isolation by what the code could reach, not by what it is meant to do. Model-authored code needs a container at minimum.
  • Credential scope matters more than process isolation. Hostile code inside a container with your token does not need to escape it.
  • Sandbox output is untrusted input. Return enums and capped lengths, and wrap what comes back as untrusted.
  • Pin images by digest and version scripts with the skill, or quality drifts with no code change to blame.
  • A fresh container per iteration inside a bounded loop is a latency bill worth measuring before you pay it.
