Tool Design for Agents

Typed schemas, errors that guide the next call, and knowing when not to add one

The schema is the only thing the model sees

A model cannot read your implementation. Whatever the schema fails to express, the model has to guess.

This is the whole discipline in one sentence, and it explains most bad tool calls. The commonest mistake is a permissive parameter type that carries no information at all.

value: Any is not a contract

Symptom: the model writes "0.5" where a float is expected, or a velocity in the wrong units, and the failure surfaces much later as a confusing solver error rather than a clear rejection.

Cause: set_field(..., value: Any) compiles to an empty JSON Schema {}. A model calling it sees no type, no unit, and no range, so it is guessing.

Mitigation: build a typed field schema from the system's own reflection at worker start, and coerce or reject every value in your wrapper before the call ever reaches the backing API.

Weak Strong What the model gains
value: Any value: float with unit in the description Type and unit, so no guess
kind: str kind: RemediationKind (enum) The full set of legal values
step: str step: str + validation naming valid steps Membership, via the error path
content: bytes content: FileRef (a URI) A 2 GB mesh never enters the context window
An enum field constrains generation directly; a bare string constrains nothing.

Errors are prompts

The model reads your error message and immediately decides what to do next, so the message should say what would work.
# Names the problem. The model has to guess the fix.
raise ValueError("invalid step")

# Names the problem and enumerates the way out.
raise ValueError(f"unknown step {step!r}; known: {sorted(schema.steps)}")

The second message turns a failure into a correction. Feeding it back as context means the model fixes itself in one retry instead of looping through plausible guesses. Cap the enumeration at a reasonable count so a schema with 400 fields does not produce a 400-item error.

Error carries Effect on the next call
What was wrong The model knows it failed
What the valid options are The model can pick correctly
Whether retrying is pointless Your retry policy can stop burning tokens
A validation failure should be marked non-retryable so it triggers a replan, not a repeat of the identical prompt.

Asymmetric returns, and the handle problem

A tool that sometimes returns a result and sometimes returns nothing at all is where agents quietly break.

In the running system, a short transaction returns its value on the same call, while a long-running one hands back a handle and nothing else. A shipped tool surface that returns bare None for the long-running case gives the model no way to tell "done, no output" from "started, come back later".

Two rules follow. Never let the model see an ambiguous return: the agent's wrapper converts the handle into a typed object the workflow understands, and the model is never shown a bare None. And never persist a client-side handle object, because it usually has no server-side identity and cannot be rebuilt in another process.

A handle you cannot pick back up

Symptom: after a worker restart, nothing can retrieve the result of a transaction that is still running.

Cause: the handle is a client-side object with no server identity, rebuilt from private attributes on a proxy. Its wait/return value cannot be retrieved from a different context than the one that launched it.

Mitigation: persist the identifiers (project, step, transaction) as the durable key and reconstruct state from a fresh status read on every poll.

Never put a file through the model

A tool signature taking raw bytes means the file's contents become tokens.
Uploading a 2 GB mesh through the model

Symptom: an upload step fails outright, or silently consumes most of the context window before the transaction that needs the file even runs.

Cause: a signature like upload_file(content: bytes) puts the file's bytes into the tool-call arguments. Fine for a kilobyte config, unworkable for a CAD mesh.

Mitigation: the tool takes a FileRef, an object-storage URI. Your executor streams the transfer directly between object storage and the backing service, and the model only ever reasons about a URI string.

This generalises. Any argument whose size is unbounded by the domain should be a reference, and any result that could be large should be a reference plus a summary. That is the claim-check pattern, and it applies to logs, plans and approval payloads as much as to files.

Idempotency belongs in the tool layer

Retries are automatic, so a tool that submits work needs a ledger check before it acts.
def run_transaction(client, project, step, transaction, args, *,
                    idempotency_key: str, long_running: bool):
    if already_applied(idempotency_key):
        return load_handle(idempotency_key)      # resume, never resubmit
    step_proxy = getattr(client.get_project(project).steps, step)
    result = getattr(step_proxy, transaction)(**args)
    handle = RunHandle(project, step, transaction, step_proxy._url,
                       datetime.now(timezone.utc))
    record(idempotency_key, handle)
    return handle if long_running else result

The key is derived from identifiers the caller already has, such as run ID, step ordinal and transaction name, so it computes identically on every retry. A UUID generated inside the function is a different key each attempt and protects nothing. See Agentic Workflows.

New tool or new skill?

Add a tool when the model lacks a verb. Add a skill when it has the verbs and lacks the judgement.
Situation Answer Why
No way to check whether a step is genuinely done New tool A missing capability; no playbook substitutes for it
Knowing what to do when a solver diverges New skill The verbs exist; the judgement does not
A tool growing a mode parameter with six values Probably a skill A decision tree is leaking into a signature
The model calls one primitive forty times in a row Probably a tool A missing batch verb
Confusing the two gives you either a bloated tool surface or an unusable monolithic prompt.

Keep the tool surface small. Every tool definition costs tokens on every call, and a large surface makes tool selection itself harder. See Agent Skills.

Takeaways

  • The schema is the model's only view of your function. Enums and typed fields constrain generation; Any constrains nothing.
  • Write errors that enumerate valid options, and mark validation failures non-retryable.
  • Never show the model an ambiguous return, and never persist a client-side handle.
  • Pass file references, never bytes.
  • Put the idempotency check in the tool wrapper, keyed by identifiers the caller already has.
  • A missing verb is a tool. Missing judgement is a skill.
