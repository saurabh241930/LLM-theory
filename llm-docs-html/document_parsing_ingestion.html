Document Parsing & Ingestion

The stage before chunking, where most retrieval quality is won or lost

Every RAG tutorial starts from clean text

Real corpora are PDFs with multi-column layouts, tables that carry the answer, and figures with captions that explain them. The chunker runs downstream of a parser nobody teaches.

A naive PDF text extractor reads a two-column page as interleaved lines, flattens a table into a run of numbers with no headers, and drops figure captions entirely. Everything downstream inherits that damage. You can tune chunk size and reranking forever and never recover a table whose column headers were lost at extraction.

The practical consequence: measure parse quality before tuning retrieval. If tables are the answer and tables are broken, retrieval tuning is the wrong knob.

Parser choice by document type

Pick the cheapest parser that preserves the structure your questions need.
Document type Parser Preserve Cost
HTML documentation DOM-aware extraction Heading hierarchy, table structure, anchors Near zero
Born-digital PDF Layout-aware text extraction Reading order, columns, table cells Low
Scanned PDF OCR plus layout analysis Everything; nothing exists as text yet Moderate, and error-prone
Pages where figures carry meaning Vision model over the page image Diagram semantics, chart values High; use selectively
Logs and structured output Line-oriented, format-specific Line prefixes, error anchors, timestamps Near zero
Vision parsing is powerful and expensive; route pages to it rather than running it over a whole corpus.

Routing matters more than picking one parser. A documentation set is mostly prose that a cheap extractor handles perfectly, with a small fraction of pages where a diagram is the answer. Detecting those and sending only them to a vision model keeps the bill proportional to the value.

Tables are the case that breaks naive pipelines

A table flattened to text loses the row-column relationship that was the entire content.

"Error 217 | licence checkout failed | restart the licence daemon" is three related cells. Flattened into prose and split across a chunk boundary, the error code can end up in one chunk and its remediation in another, and neither is retrievable as an answer.

  • Never split a table across chunks. A table is an atomic unit, the same way a skill file is.
  • Serialise to a structure-preserving format. Markdown tables or HTML keep the header-to-cell relationship in the token stream, so the model can read down a column.
  • Repeat headers in every chunk when a long table genuinely must be split, so each fragment stands alone.
  • Carry a caption. "Table 3.1: Failure taxonomy" is retrieval signal the rows themselves do not contain.

The same reasoning applies to figures. A diagram is retrievable through its caption and surrounding text, so keep them attached to whatever representation of the figure you store.

Two stages deserve attention because they are commonly placed wrong.

Contextualisation belongs at ingest, before embedding. A chunk is written once and read thousands of times, so a per-chunk model call amortises to nothing. Computing the same context at query time repeats the work on every request. It also improves keyword search, because the preamble contributes the product and version tokens the fragment was missing.

Scrubbing belongs before embedding, not before display. Scrubbing at render time leaves the removed detail encoded in the vector, where it can still influence retrieval and still sits in your index.

Incremental ingest

Diff by content hash so a release re-embeds the pages that changed, not the corpus.

A documentation release typically changes a small fraction of pages. Hashing parsed content per document and comparing against the previous run turns a full re-index into a modest incremental job, which is what makes per-release refresh affordable at all.

Hash the parsed content rather than the raw file. A PDF regenerated with a new timestamp has a different file hash and identical content, and hashing the file would re-embed the whole corpus on every release.

Change detected Action
New document Parse, chunk, embed, index
Content hash changed Re-chunk and re-embed; set valid_to on the old chunks
Unchanged Skip; update the version tag only
Document removed Set valid_to; retain for audit
Retirement uses a validity window rather than a delete, so audit survives.

Failure modes in ingestion

Ingestion fails quietly. Nothing errors; answers just get worse.
Silent parser regression

Symptom: retrieval quality drops after a documentation site redesign, with no change to any retrieval code.

Cause: heading-boundary chunking depends on HTML structure. A redesign that changes heading levels produces chunks of an entirely different shape.

Mitigation: assert distribution properties at ingest (median chunk size, share of chunks under a floor, count of extracted tables) and fail the ingest run when they move sharply, rather than discovering it through degraded answers weeks later.

OCR errors becoming permanent

Symptom: queries for a specific error code never match, though the code is clearly in the source document.

Cause: OCR read 217 as 2l7. Keyword search cannot match it, and the embedding for a corrupted token is meaningless.

Mitigation: validate extracted identifiers against known patterns for the domain, flag low-confidence OCR regions for review, and prefer born-digital sources whenever both exist.

Ingest that is not idempotent

Symptom: a re-run after a partial failure produces duplicate chunks, and retrieval returns the same passage three times in a top-8 slate.

Cause: the ingest job appends rather than upserting, keyed by nothing stable.

Mitigation: key chunks by a deterministic ID derived from document URI, version and ordinal, and upsert. A re-run then repairs rather than duplicates.

Takeaways

  • Measure parse quality before tuning retrieval. A lost table header cannot be recovered downstream.
  • Route pages to parsers by type. Send only figure-bearing pages to a vision model.
  • Never split a table across chunks, and keep headers and captions attached.
  • Contextualise and scrub before embedding, not at query or render time.
  • Diff by hash of parsed content so a release re-embeds only what changed.
  • Assert chunk distribution properties at ingest; parser regressions are otherwise silent.
